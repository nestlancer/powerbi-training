Why IoT & Lab Sensors Use Sentinel Codes Like -200:
Old industrial loggers couldn't write blank cells, so whenever a gas analyzer went offline for calibration, it logged -200. Look at what happens if you take a raw average without converting -200 to null:
• CO(GT) has 1,683 -200 readings (18.0%) → Raw Average = -34.21 mg/m³ (negative air pollution is physically impossible!) → Clean Average = 2.15 mg/m³.
• NMHC(GT) has 8,443 -200 readings (90.2% offline!) — that reference analyzer failed permanently in May 2004 and must be quarantined/dropped.
• Sheet AirQualityUCI also has 114 empty formatted rows at the bottom (rows 9,359–9,472) that you must remove!

4. Phase A — Step-by-Step in Microsoft Excel

Step A1 — Save a Working Copy & Replace Exact -200 Cells with Blank

Open datasets/10-air-quality/data/AirQualityUCI.xlsx and immediately click File → Save As → 10-air-quality-clean.xlsx (keep original untouched!).
Select columns C:O → press Ctrl + H (Find & Replace):
  • Find what: -200
  • Replace with: (leave completely empty!)
  • Click Options >> and CHECK Match entire cell contents! (Crucial — without this, values like 1200 would get mangled!)
  • Click Replace All. Excel ignores blank cells inside AVERAGE() automatically!
💡 Why do we do this?

Reason: -200 is not a pollution reading — it's a sentinel code meaning "analyzer offline for calibration". Old industrial loggers couldn't write blanks, so they wrote -200 for every offline hour. Treating it as a number poisons everything: CO's raw average computes to -34.21 mg/m³ — literally claiming the air has negative pollution, which is physically impossible and instantly discredits the whole report to any engineer.

Real-time example: The Match entire cell contents checkbox is the quiet hero: without it, Find & Replace does substring matching — so sensor reading 1200 becomes 1 (the "200" inside got replaced!), and -2000 becomes a blank. One unchecked box silently corrupts hundreds of valid readings, and the corrupted values still LOOK plausible. This is why data engineers replace sentinels with blank/null, never zero: 0 would mean "we measured zero pollution for 1,683 hours" — a fake fact — while blank means "we don't know", which is the truth.

What happens if you skip it: Raw averages go negative, breach counts get computed over fake zeros (Mistake 1: CO average drops from 2.15 to a wrong 1.77), and the engineering team rejects the entire dashboard on sight.

Smart-work tip: Before averaging ANY sensor/machine-logged column, scan for its minimum: MIN = -200 screams sentinel. Then Save-As a working copy FIRST — one wrong Replace All on an original file is unrecoverable.

Step A2 — Verify Clean Averages & Breach Counts with Formulas

// Clean CO(GT) Average:
=AVERAGE(C2:C9358)                 --> 2.15 mg/m³

// Clean NO2(GT) Average:
=AVERAGE(J2:J9358)                 --> 113.08 µg/m³

// EU 1-Hour NO2 Directive Breaches (> 200 µg/m³):
=COUNTIF(J2:J9358, ">200")         --> 388 hours

// High Carbon Monoxide Alert Hours (> 4.0 mg/m³):
=COUNTIF(C2:C9358, ">4")           --> 812 hours

// CO(GT) Sensor Uptime %:
=COUNT(C2:C9358) / 9357            --> 82.0% (7,674 valid hours)
💡 Why do we do this?

Reason: These five formulas are the acceptance tests for the cleaning you just did — and they each prove something different. AVERAGE proves sentinels became blanks (2.15, not -34.21). The two COUNTIFs quantify regulatory compliance (388 EU NO2 breach hours, 812 high-CO hours) — numbers the client's brief explicitly demands. And the uptime formula converts "how much data survived?" into a percentage, which is how sensor engineers actually talk.

Real-time example: Watch what the numbers now say: CO averages 2.15 mg/m³ with only 82.0% uptime — meaning the reference analyzer was offline for nearly 3 weeks of the year, and every report using it must disclose that. NO2 exceeded the EU's legal 200 µg/m³ limit for 388 hours — that's a compliance finding, not a statistic. Recording these five values in Excel BEFORE building Power BI gives you fixed targets: if your DAX cards later disagree with 2.15 / 113.08 / 388 / 812, you know the model — not the physics — is wrong.

What happens if you skip it: The dashboard gets built without knowing what "correct" looks like, and a subtle null-handling mistake (e.g., text-typed numbers, half-replaced sentinels) produces plausible-looking but wrong averages that nobody catches.

Smart-work tip: After ANY cleaning step, immediately compute the clean summary statistics — cleaning without verification is just moving errors around. Uptime % (valid ÷ total) is a metric worth keeping permanently: it turns data quality into a number leadership can track.

5. Phase B — Complete Power BI & Charts Journey

Stage 1 & 2 — Multi-Column Sentinel Cleaning in Power Query

  1. Click Home → Excel workbook → select data/AirQualityUCI.xlsx → check sheet AirQualityUCI → click Transform Data. Rename query to AirQuality.
  2. Step 1 — Strip the 114 Trailing Blank Rows: Click Home → Remove Rows → Remove Blank Rows (or filter Date to uncheck null). Row count becomes exactly 9,357!
  3. Step 2 — Drop the 90.2%-Dead Sensor: Right-click column NMHC(GT) → Remove.
  4. Step 3 — Replace -200 with null Across ALL 12 Remaining Sensor Columns at Once! Click column CO(GT), hold Shift, and click column AH so all 12 numeric columns are highlighted together! Right-click any selected header → Replace Values → Value To Find: -200 → Replace With: null (lowercase!) → click OK.
  5. Step 4 — Extract Clean Hour (0–23): Click column Time → set Data Type = Time → click Add Column → Time → Hour → Hour. Set Date = Date.
  6. Click Home → Close & Apply.
💡 Why do we do this?

Reason: This is a full data-quality audit disguised as an import routine, and the order matters: (1) remove the 114 formatted-but-empty rows so counts are honest (9,357, not 9,471); (2) quarantine the permanently-failed NMHC(GT) sensor — 90.2% of its data is -200, so it's not a column with gaps, it's a dead instrument that would inject noise into every visual it touches; (3) sentinel-to-null across ALL 12 columns in one Shift-click selection — the refreshable equivalent of Excel's Replace All; (4) extract Hour because every question in the brief ("rush-hour smog profile") is indexed by hour-of-day.

Real-time example: The NMHC decision is the professional judgment call worth studying: keeping it means every chart risk showing garbage averages over 9.8% real data; dropping it loses 1 column entirely. Engineers quarantine instruments exactly like this — the log shows the analyzer failed permanently in May 2004, so the column isn't "sparse data", it's a broken device. Also note lowercase null: Power Query's M language is case-sensitive, and NULL (uppercase) inserts the literal TEXT "NULL" into your numeric column, breaking every average (Mistake 2).

What happens if you skip it: Blank dates appear in slicers, the dead sensor pollutes averages, uppercase NULL corrupts 12 numeric columns into text, and the Hour column never exists so the diurnal chart can't be built.

Smart-work tip: Judge a column by its VALID share, not its existence: <50% valid → quarantine and document; ≥95% valid → keep and report uptime. Column-level data-quality triage is a repeatable professional routine — the column dictionary's "-200 Count" column is exactly that audit, pre-computed for you.

Stage 3 & 4 — Environmental KPI DAX Measures

Total Monitored Hours = COUNTROWS ( 'AirQuality' )
// Check: 9,357

Avg CO (mg/m3) = AVERAGE ( 'AirQuality'[CO(GT)] )
// Check: 2.15 (DAX AVERAGE automatically skips nulls!)

Avg NO2 (ug/m3) = AVERAGE ( 'AirQuality'[NO2(GT)] )
// Check: 113.08

Avg Benzene (ug/m3) = AVERAGE ( 'AirQuality'[C6H6(GT)] )
// Check: 10.08

Avg Temp (C) = AVERAGE ( 'AirQuality'[T] )
// Check: 18.32 °C

CO Sensor Uptime % =
DIVIDE ( COUNT ( 'AirQuality'[CO(GT)] ), [Total Monitored Hours] )
// Check: 82.0% (vs 96.1% for PT08.S1!)

EU NO2 Breach Hours =
CALCULATE ( COUNTROWS ( 'AirQuality' ), 'AirQuality'[NO2(GT)] > 200 )
// Check: 388 hours

High CO Alert Hours =
CALCULATE ( COUNTROWS ( 'AirQuality' ), 'AirQuality'[CO(GT)] > 4.0 )
// Check: 812 hours
💡 Why do we do this?

Reason: Notice what these measures do NOT do: none of them sum a pollution reading — concentrations are averaged, because "total CO of the year" is physically meaningless. CO Sensor Uptime % divides COUNT (which counts only non-null values) by COUNTROWS (all monitored hours) — that contrast between the two counting functions IS the uptime calculation. The breach measures wrap threshold conditions in CALCULATE so they respond to every slicer (weekends, months, date ranges) while always enforcing the legal limit.

Real-time example: Trace one number through the pipeline: Excel said CO = 2.15 mg/m³; Power BI's AVERAGE — which automatically skips nulls — lands on exactly 2.15 again. That agreement certifies that the Power Query null-replacement replicated the Excel cleanup perfectly (including the lowercase-null subtlety). Meanwhile EU NO2 Breach Hours gives the environmental team a legal-grade number: 388 hours above the EU directive limit, filterable by month or weekday — a static Excel COUNTIF could never slice.

What happens if you skip it: If uptime isn't reported, decision-makers can't weigh how much they trust the averages; if breach conditions live in visual filters instead of measures, the count changes when someone rescales an axis — compliance numbers must come from measures, never from formatting.

Smart-work tip: Use COUNT vs COUNTROWS deliberately: the gap between them is always your null share. And encode regulatory thresholds (200 µg/m³, 4.0 mg/m³) directly in measures or as constant measures — one definition, every visual consistent.

💡 Why do we do this?

Reason: The diurnal (24-hour) curve exists because pollution is behavioral — it follows human traffic, not random weather. Plotting average CO per hour-of-day turns 9,357 messy rows into one readable daily rhythm. The Analytics constant line adds the decision boundary: a threshold ON the chart converts "the peak is 3.73" into "the evening peak CROSSES our 3.0 alert level" — a statement someone can act on. Lines from the Analytics pane are also visual-native: they recompute correctly when slicers filter the data.

Real-time example: Read the curve like the smart-city team: trough at 05:00 (0.71 mg/m³ — empty pre-dawn streets), morning rush spike at 09:00 (2.97), evening peak at 19:00 (3.73 — when commuting and evening traffic stack up). The dashed red line at 3.0 shows that only the 18:00–20:00 window breaches it on an average day — which directly targets the client's intervention: congestion pricing or traffic-light retiming aimed at the evening window, not blanket restrictions. Without the threshold line, the peak reads as trivia; with it, the peak reads as a trigger.

What happens if you skip it: The audience sees a wave with no reference — is 3.73 high? Dangerous? Normal? Without a benchmark, every viewer invents their own threshold, and the meeting drifts.

Smart-work tip: Analytics-pane lines (constant, average, min/max, trend) are professional-grade because they're bound to the data, not drawn by hand — prefer them over the old trick of adding a fake "threshold table" to the legend. One chart, one clear question; here: "when does average pollution cross the alert line?"

💡 Why do we do this?

Reason: This is a calibration study, the classic use of a scatter chart: X = the expensive reference analyzer (ground truth), Y = the cheap IoT sensor, each point = one hour. If the cloud hugs a rising trend line, the low-cost sensor is a valid proxy; if the cloud is diffuse, it isn't. The Analytics trend line gives the visual its statistical claim without leaving Power BI.

Real-time example: This visual answers a real purchase decision: "Can we deploy 100 more PT08.S1 sensors at €50 each instead of reference analyzers at €5,000 each?" The tight upward slope says yes — the tin-oxide sensor tracks true CO. The uptime comparison sharpens it: the IoT unit was online 96.1% of hours vs the reference analyzer's 82.0% — the "cheap" sensor is actually the MORE reliable instrument. An engineer can now justify the IoT rollout with evidence, not vendor brochures. Note the practical trick too: 9,357 hourly points render slowly, so using the Index column or daily averages keeps the scatter responsive.

What happens if you skip it: The team debates sensor accuracy anecdotally ("seems okay I guess") and the IoT expansion decision stalls or gets made on marketing claims.

Smart-work tip: Whenever one column is "truth" and another is a "candidate measurement", scatter + trend line is the pattern (sensor vs lab, forecast vs actual, model vs observed). If you need more rigor later, compute a correlation coefficient in DAX — but the visual alone carries most of the argument.

Visual 4 & 5 Winter Inversion Combo Chart + Top Breach Hours Table

1. Line and clustered column chart: X-axis = Date (Year + Month hierarchy), Column Y-axis = [EU NO2 Breach Hours], Line Y-axis = [Avg Temp (C)]. Notice how breaches skyrocket in cold winter months (Nov–Feb) when cold air traps vehicle exhaust near street level!
2. Table: List Date, Hour, CO(GT), NO2(GT), C6H6(GT), and T sorted by NO2(GT) descending (peaking at 339.7 µg/m³!).

💡 Why do we do this?

Reason: The winter combo tests a hypothesis: if temperature inversions drive smog, breach hours and temperature should move in opposite phase — high columns when the line dips. The breach-hours table then serves the enforcement workflow: regulators don't act on monthly averages; they cite specific episodes (exact date, hour, reading) when fining or issuing alerts.

Real-time example: Read the combo and the physics appears: Nov–Feb columns tower while the temperature line sinks — cold air layers trap exhaust at street level (the "inversion" effect), so the same traffic produces double the pollution. That's a causal argument a city planner can budget against: winter-focused traffic measures, not year-round ones. The table then documents the smoking gun: the worst hour peaked at 339.7 µg/m³ of NO2 — 70% over the EU limit — with its date and hour on record for the official file. Statistics motivate; episodes prosecute.

What happens if you skip it: "Breaches happen more in winter" stays a hunch nobody can show to a council committee, and enforcement has no evidentiary table — just charts.

Smart-work tip: When testing a suspected driver (temperature → pollution), plot the suspected cause and effect on SEPARATE axes of one combo chart — inverse phase jumps out. And always pair aggregate visuals with one sorted detail table; that's where "show me the worst case" questions get answered without leaving the page.
