4. Phase A — Step-by-Step in Microsoft Excel (Performance Survival Rules!)

Step A1 — Why 542,000 Rows Need Power Pivot / PivotTables & Matrix (Not Volatile Formulas)

Open datasets/14-online-retail/data/Online Retail.xlsx (give Excel 8–12 seconds to unpack 541,909 rows!). Add just two lightweight columns:
• I2 (LineAmount): =D2*F2
• J2 (EntryType): =IF(LEFT(A2,1)=\"C\",\"Credit Note\",IF(F2<0,\"Bad Debt\",IF(D2>0,\"Gross Sale\",\"Stock Adj\")))
You'll see: I2 shows 15.3 — the workbook stores raw General-format numbers, so no currency symbol appears anywhere (row 2: 6 × 2.55). J2 shows the text Gross Sale (invoice 536365 starts with 5, not C). Before building the PivotTable, format column I as Currency £#,##0.00 so the totals display as the £ figures below.
Insert a PivotTable with EntryType in Rows and Sum of LineAmount in Values: verify Gross Sale = £10,666,684.54, Credit Note = -£896,812.49, Bad Debt = -£22,124.12, and Grand Total = £9,747,747.93!
The Power BI Matrix Visual independently confirms the same four buckets and totals!
💡 Why do we do this?

Reason: At half a million rows, Excel strategy changes: volatile formulas (VLOOKUP chains, whole-column references) recalculate on every edit and freeze the workbook — the client's exact complaint. Two small helper columns + one PivotTable is the scale-appropriate pattern: the pivot's engine summarizes 541,909 rows in memory without touching a single other cell. The EntryType classification is the intellectual core: raw ERP lines mix sales, returns (invoices prefixed \"C\"), and write-offs (negative prices, prefixed \"A\") — until you LABEL them, a simple SUM produces a number that is neither gross nor net and answers no finance question. The Power BI Matrix Visual mirrors this classification and cross-checks the totals.

Real-time example: Watch the reconciliation logic come alive: Gross Sale £10,666,684.54 − Credit Notes £896,812.49 − Bad Debt £22,124.12 = £9,747,747.93 — the exact number the FD will sign off. That's not rounding luck: the classification is complete (every row lands in exactly one bucket), so the buckets MUST sum to the ledger total. When Power BI reproduces all four numbers, you've proven the whole model to the penny — and the 8.41% return rate emerges as a real KPI rather than a buried column.

What happens if you skip it: Unlabeled negatives pollute \"revenue\" (beginners report £9.75M as \"gross\" or panic at negative lines), and nobody can separate \"customers returning goods\" from \"accounting write-offs\" — two completely different management problems.

Smart-work tip: At 100K+ rows, prefer pivot summaries over formula floods, and classify transaction types as DATA (a column), not as separate formulas per question. One EntryType column now answers every \"how much was returns?\" question forever. The PivotTable and Matrix are the cheap insurance that stops nonsense from ever reaching a chart.

5. Phase B — Complete Power BI & 80/20 Pareto Journey

Stage 1 & 2 — High-Speed Power Query Cleaning (Zero Pre-Calculated Line Column Needed!)

  1. Click Home → Excel workbook → select data/Online Retail.xlsx → check Online Retail → Transform Data. Rename query to Retail.
  2. Important Type Check: Ensure InvoiceNo, StockCode, and CustomerID are all ABC (Text)! (Because InvoiceNo has C536379 and StockCode has 85123A!)
  3. Replace null in CustomerID with \"Guest\".
  4. In Country, use Replace Values: EIRE → Ireland, RSA → South Africa, Channel Islands → United Kingdom.
  5. Add Conditional/Custom Column EntryType: 
    if Text.StartsWith([InvoiceNo], "C") then "Credit Note"
else if [UnitPrice] < 0 then "Bad Debt"
else if [Quantity] > 0 and [UnitPrice] > 0 then "Gross Sale"
else "Stock Write-Off"
  6. Extract OrderDate (Date Only) from InvoiceDate. Click Home → Close & Apply — watch Power BI's VertiPaq engine compress 541,909 rows into ~12 MB in seconds!
💡 Why do we do this?

Reason: Four quiet landmines get defused. (1) Types: InvoiceNo contains C536379 and StockCode contains 85123A — force them to Text or the C-prefixed credit notes become Error cells and -£896,812 of returns silently vanishes, overstating revenue by 9% (Mistake 1 exactly). (2) Guests: 135,080 blank-CustomerID lines are real £1.45M walk-in/guest sales — labeling them \"Guest\" preserves them instead of dropping 25% of rows. (3) Country codes: EIRE, RSA, and Channel Islands are customs abbreviations — without mapping, \"EIRE\" plots nowhere on a map and Ireland's £263K disappears from the export story. (4) The EntryType conditional column moves the classification into refreshable Power Query.

Real-time example: Consider what each fix buys: keeping guests means the Registered-vs-Guest chart (Visual 5) can reveal that 24.9% of all invoice lines — £1.45M, about 14.9% of net revenue — come from customers you can't remarket to. Fixing EIRE means the export map shows Ireland correctly instead of dropping it — which changes the \"top export market\" ranking. Small mapping edits, big strategic numbers.

What happens if you skip it: Numbers become Error cells, 25% of rows vanish, two countries vanish from maps, and the whole reconciliation drifts from the Excel checkpoint.

Smart-work tip: Scan identifier columns for letters BEFORE letting any import guess types — \"IDs with prefixes/suffixes must be Text\" is a law, not a preference. And never treat blanks in a key column as deletable; ask what business reality the blank represents (here: guest checkout) and LABEL it.

Stage 3 & 4 — Calendar Table + Gross/Net & 80/20 Pareto DAX

Create a Calendar table (2010-12-01 to 2011-12-09) and relate Calendar[Date] → Retail[OrderDate]. Then write:

Net Revenue =
SUMX ( 'Retail', 'Retail'[Quantity] * 'Retail'[UnitPrice] )
// Check: £9,747,747.93

Gross Sale =
CALCULATE ( [Net Revenue], 'Retail'[EntryType] = "Gross Sale" )
// Check: £10,666,684.54

Credit Note =
CALCULATE ( [Net Revenue], 'Retail'[EntryType] = "Credit Note" )
// Check: -£896,812.49

Bad Debt =
CALCULATE ( [Net Revenue], 'Retail'[EntryType] = "Bad Debt" )
// Check: -£22,124.12

Guest Revenue =
CALCULATE ( [Net Revenue], 'Retail'[CustomerID] = "Guest" )
// Check: £1,450,000.00 (24.9% of lines)

Pareto 80/20 Check =
VAR RankedCustomers =
    TOPN (
        ROUND ( COUNTROWS ( VALUES ( 'Retail'[CustomerID] ) ) * 0.20, 0 ),
        VALUES ( 'Retail'[CustomerID] ),
        [Net Revenue], DESC
    )
RETURN
DIVIDE (
    CALCULATE ( [Net Revenue], RankedCustomers ),
    [Net Revenue]
)
// Check: ≈ 80%
💡 Why do we do this?

Reason: The measures mirror the Excel PivotTable audit exactly. The classification (Gross / Credit / Bad Debt) ensures the Net Revenue (£9,747,747.93) matches the ledger. The Guest Revenue (£1.45M) isolates walk-in sales. The Pareto check computes the 80/20 rule: ranking customers by Net Revenue and summing the top 20% yields ~80% of total revenue — the client's strategic benchmark.

Real-time example: The finance director sees that 20% of customers generate 80% of revenue (£7.8M out of £9.75M), while 135,080 guest lines (£1.45M) represent walk-in traffic that can't be remarketed. The PivotTable and Matrix independently confirm the £9,747,747.93 Net Revenue and the four buckets, proving the model integrity.

What happens if you skip it: The 80/20 rule is guessed (not calculated), guest sales vanish (25% data loss), and the Net Revenue drifts from the £9,747,747.93 checkpoint. The PivotTable and Matrix audit is the only insurance against these errors.

Smart-work tip: Always audit classification buckets (Gross / Credit / Bad Debt) in both Excel PivotTable and Power BI Matrix before building Pareto or customer rankings. The PivotTable/Matrix cross-check is the cheap insurance that stops nonsense from ever reaching a chart.
