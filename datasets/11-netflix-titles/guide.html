\n Three Real-World Dirty-Text Traps in netflix_titles.csv:
\n 1. 88 Leading Spaces in date_added: Rows like \" August 14, 2020\" begin with a space! Always run Transform → Format → Trim BEFORE parsing as a Date (English - United States locale).
\n 2. Mixed Units in duration: Column J stores both \"90 min\" (for Movies) and \"4 Seasons\" (for TV Shows). Split by space into DurationNum + DurationUnit and filter by type before averaging!
\n 3. Comma-Separated Multi-Value Genres (listed_in): A single title has up to 3 genres (e.g., \"International Movies, Dramas, Comedies\"). Splitting into rows inside a 2-column TitleGenres bridge table lets you rank true individual genres (International Movies = 2,437, Dramas = 2,106)!\n

4. Phase A — Step-by-Step in Microsoft Excel

\n\n

Step A1 — Import UTF-8 CSV & Add Clean Helper Columns

\n
\n Open Excel → Data → From Text/CSV → select datasets/11-netflix-titles/data/netflix_titles.csv → File Origin: 65001: Unicode (UTF-8) (so international titles like João Miguel render cleanly!) → Load. Add helper columns:\n
// Col M (YearAdded) — trims leading space and extracts 4-digit year:\n=IF(G2=\"\",\"\", VALUE(RIGHT(TRIM(G2), 4)))\n\n// Col N (PrimaryCountry) — text before first comma, or \"Unknown\":\n=IF(F2=\"\",\"Unknown\", IFERROR(LEFT(F2, FIND(\",\",F2)-1), F2))\n\n// Col O (DurationNum) — integer before first space:\n=VALUE(LEFT(J2, FIND(\" \", J2)-1))
\n
\n
\n
💡 Why do we do this?
\n

Reason: Three invisible traps are being disarmed at the door. (1) Encoding: without File Origin = UTF-8, international names like João Miguel or Korean titles arrive as mojibake (JoÃ£o) — and mojibake can't be searched, grouped, or joined reliably. (2) Whitespace: the 88 leading spaces in date_added would make RIGHT(TRIM(G2),4) wrong without TRIM, and would block every date parse. (3) Mixed units: duration stores \"90 min\" AND \"4 Seasons\" in one column — so DurationNum extracts the number and type decides whether it means minutes or seasons. One number, two meanings, and averaging it blindly would average minutes with seasons.

\n

Real-time example: Why the helper columns are worth it: PrimaryCountry (text before the first comma) converts \"United States, Ghana, United Kingdom\" — a co-production — into the one country analysts will chart; without it, the same title counts as 3 different \"countries\" and country bars double-count. DurationNum is what lets Excel compute AVERAGEIF(type=\"Movie\") = 99.3 minutes — an answer the raw string column can never give.

\n

What happens if you skip it: Dates fail to parse (or parse as the wrong month/day order), international titles become unsearchable garbage, and the 99.3-minutes metric is impossible without the numeric split.

\n

Smart-work tip: When importing international data, set encoding FIRST — it's the one mistake you can't fix by re-reading the column later. And whenever one column packs number + unit (\"90 min\"), split into value + unit and let a type column disambiguate before averaging anything.

💡 Why do we do this?

Reason: These aren't trivia — they're the benchmarks the entire dashboard must reproduce, computed with the right tool for each question: PivotTable and Matrix for category counts and type-specific averages (the only safe way to average DurationNum while it holds both minutes and seasons). Doing this in Excel and Power BI first means you know the truth before Power BI can disagree with it.

Real-time example: The numbers already sketch the strategy story: the library is 69.1% movies at 99.3 minutes (Netflix's original DVD-era DNA is film licensing), but the TV side carries the surprise — 66.7% of shows have only 1 season (1,608 of 2,410). That's the "cancellation/miniseries rate" card: two-thirds of Netflix series never get a season 2 — an acquisition-committee talking point about risk and churn that falls out of two simple formulas. Without PivotTable/Matrix-by-type, the movie average would be poisoned by the 1.78-season values and read something meaningless like 27.4.

What happens if you skip it: You discover in Power BI that averages look wrong (mixing units) and spend the afternoon debugging what a 3-line Excel check would have flagged in a minute.

Smart-work tip: Whenever a numeric column has mixed semantics (minutes vs seasons, kg vs lb), compute each semantic group's average separately BEFORE trusting any overall average. PivotTable and Matrix are the cheap insurance that stops nonsense from ever reaching a chart.

5. Phase B — Complete Power BI & Charts Journey

Stage 1 & 2 — Clean Titles + Build TitleGenres Bridge Table in Power Query

  1. Click Home → Text/CSV → select data/netflix_titles.csv (UTF-8) → Transform Data. Rename query to Titles.
  2. Fix date_added: Select date_added → Transform → Format → Trim → right-click header → Change Type → Using Locale → Data Type: Date, Locale: English (United States). Then click Add Column → Date → Year → Year (name: YearAdded).
  3. Extract PrimaryCountry: Replace blank/empty values in country with Unknown → click Add Column → Extract → Text Before Delimiter → Delimiter: , → rename to PrimaryCountry.
  4. Split duration: Select duration → Transform → Split Column → By Delimiter → Space (Left-most delimiter) → rename to DurationNum (Whole Number) and DurationUnit.
  5. Build the Exploded Genre Bridge Table (Pro BI Technique!):
    • In the left Queries pane, right-click Titles → click Reference → rename the new query to TitleGenres.
    • Hold Ctrl and click show_id and listed_in → right-click → Remove Other Columns.
    • Select listed_in → Transform → Split Column → By Delimiter → Delimiter: Comma → expand Advanced options → choose Rows (NOT Columns!) → click OK!
    • Click Transform → Format → Trim on listed_in and rename it to Genre.
  6. Click Home → Close & Apply.
💡 Why do we do this?

Reason: Two lessons hide here. First, Trim before locale-parse: \" August 14, 2020\" with its leading space can parse as text-but-not-date, or the wrong date — trim first, then parse with an explicit locale (US month-first format), because implicit parsing depends on your machine's regional settings and fails differently on every laptop. Second, the bridge table: one title can have up to 3 genres in a comma-joined string, and \"Split into ROWS\" (not columns!) inside a Reference query converts each title into one row per genre — turning an unanalyzable text blob into a proper 1-to-many relationship.

\n

Real-time example: Feel the difference split-rows makes: \"International Movies, Dramas, Comedies\" becomes 3 rows in TitleGenres, each pointing at the same show_id. Suddenly \"rank genres\" is a trivial bar chart: International Movies 2,437, Dramas 2,106 — the real ranking the VP asked for. Split into columns instead (Mistake 1) and each genre lands in Genre.1/Genre.2/Genre.3 depending on its position, so \"Dramas\" fragments across three columns and no single bar chart can ever count it properly.

\n

What happens if you skip it: Genre analysis stays impossible (or wrong), dates break on non-US machines, and the whole Visual 4 deliverable dies.

\n

Smart-work tip: The Reference-query bridge table is THE standard pattern for any multi-value field — genres, tags, cast members, skills, product categories. Keep the original one-row-per-title fact intact and explode multi-values into a linked detail query: both questions (\"count titles\" and \"rank tags\") get answered correctly from the same model.

Stage 3 — Connect Titles (1) → (*) TitleGenres in Model View

\n
\n Open Model view: confirm Titles[show_id] (1) connects to TitleGenres[show_id] (*), Single cross-filter direction (or Both if you want clicking a Genre bar to filter Country/Trend charts — since Titles is the only fact table here, setting Cross-filter direction = Both on this 2-table model lets clicking Dramas slice every visual on the page!).\n
\n
\n
💡 Why do we do this?
\n

Reason: The 1-to-many relationship is what makes the bridge useful: one show_id in Titles matches its 1–3 genre rows in TitleGenres, so filters can flow between \"what the title is\" and \"what genres it carries\". Cross-filter direction then decides whether the story can flow BACKWARDS: from a genre (the many side) up to titles (the one side) and onward to every other visual.

\n

Real-time example: Compare the two settings in a meeting: with Single direction (the safe default), clicking Dramas on the genre bar filters only what can flow down — basically nothing else, because the genre table has no country or year columns. With Both directions on this tiny 2-table model, clicking Dramas filters Titles → which filters the country mix, the stacked area, and the KPI cards: \"how much of the Dramas catalog is Indian?\" becomes a single click. On large multi-table models, Both-direction can create ambiguous filter paths — but here, with one fact table, it's simply the correct setting.

\n

What happens if you skip it: The genre bar chart becomes decorative — click a genre and the rest of the page ignores you, which users experience as a broken dashboard.

\n

Smart-work tip: Default to single-direction relationships and consciously upgrade specific ones to Both when a \"many-side\" category (like Genre) is meant to drive the whole page. Always test the click-through after changing direction — interactions are only real if you've seen them fire.

Stage 4 — DAX Measures

\n
Total Titles = DISTINCTCOUNT ( 'Titles'[show_id] )\n// Check: 7,787 (safe even when sliced by TitleGenres!)\n\nMovie Count = CALCULATE ( [Total Titles], 'Titles'[type] = \"Movie\" )\n// Check: 5,377\n\nTV Show Count = CALCULATE ( [Total Titles], 'Titles'[type] = \"TV Show\" )\n// Check: 2,410\n\nMovie Share % = DIVIDE ( [Movie Count], [Total Titles] )\n// Format: 0.0% -> shows 69.1%, not the raw 0.6905\n// Check: 69.1%\n\nAvg Movie Runtime (min) =\nCALCULATE ( AVERAGE ( 'Titles'[DurationNum] ), 'Titles'[type] = \"Movie\" )\n// Check: 99.3\n\nOne-Season TV Rate % =\nVAR OneS = CALCULATE ( [TV Show Count], 'Titles'[DurationNum] = 1 )\nRETURN DIVIDE ( OneS, [TV Show Count] )\n// Format: 0.0%\n// Check: 66.7% (1,608 of 2,410 TV Shows!)
\n
\n
💡 Why do we do this?
\n

Reason: Total Titles = DISTINCTCOUNT(show_id) is the load-bearing decision in this model. Because TitleGenres exploded each title into up to 3 rows, any naive COUNTROWS under a genre context reports the number of GENRE TAGS, not titles — 17,071 tags, not 7,787 titles (Mistake 2 exactly). DISTINCTCOUNT collapses back to unique shows no matter how the bridge slices the data. The other measures follow the earlier patterns: CALCULATE-filtered averages per type (units discipline), and a VAR-based ratio for the 1-season rate.

\n

Real-time example: Watch the measure save the genre chart: clicking Dramas (2,106 tags) with DISTINCTCOUNT returns the number of unique Drama titles — the correct business question — while COUNTROWS would have returned tag-rows including titles counted 2–3 times. Same discipline protects the KPI strip when a user filters by genre: the \"Total Library\" card must still say 7,787 with no filter and a correct smaller number with one. That is what \"measure is correct in every filter context\" means concretely.

\n

What happens if you skip it: The first click on any genre bar inflates every count on the page ~2.2×, and nobody notices because every number is still plausible-looking — until the VP compares against the published catalog size.

\n

Smart-work tip: The instant you build a bridge/exploded table, audit every count measure in the model and switch them to DISTINCTCOUNT of the fact key. Bridge tables change the grain of every visual they touch — the model owner must keep the \"one entity\" definition stable.

💡 Why do we do this?
\n

Reason: The acquisition question is \"how fast did the library grow, and which format drove it?\" — a parts-plus-total-over-time question, which is exactly what a Stacked Area is for (the Set 03 rule re-applied). The layer split by type shows whether Movies or TV Shows led each surge, and the total envelope answers \"how big is the catalog wave\". Note the honest exclusions baked into the filters: years before 2013 are sparse and 2021 contains only January — plotting partial periods produces fake cliffs that mislead every reader.

\n

Real-time example: Read the wave as a strategy timeline: near-flat through 2015, then an explosive climb to the 2,153-title peak in 2019 — the height of the streaming wars when Netflix outspent every rival on originals and international licensing. The layer colors show the growth was broad-based in Movies (red) with TV Shows (slate) accelerating late. An acquisition VP reading this chart immediately asks the right follow-up: \"what did we buy in 2019 that we should renew this year?\" — the chart frames renewals strategy, not just history.

\n

What happens if you skip it: With 2021's partial January included, the chart's last point collapses to ~8% of a normal year — readers conclude \"Netflix collapsed in 2021\" and the meeting derails over a data-coverage artifact.

\n

Smart-work tip: ALWAYS check the last period of any time series for partial coverage before publishing — it's the single most common time-chart lie. Either filter the partial period out (as here) or annotate it visibly.

💡 Why do we do this?
\n

Reason: Countries differ by 15× in catalog size (US 2,883 vs South Korea 194), so a normal stacked bar would make every small country invisible — the composition question (\"what's the MOVIE-vs-TV strategy per country?\") needs equal-length bars, which is precisely the 100% Stacked Bar's contract (same normalization lesson as Set 02's gender chart). Filtering to the Top 10 by size and excluding Unknown keeps the comparison honest and readable.

\n

Real-time example: The chart hands the licensing team a country playbook: India = 92.4% movies (Bollywood's film-first industry — a deal pipeline should target film packages), while South Korea = 78.4% TV shows (the K-Drama engine) and Japan = 68.4% TV (anime series). Same platform, three opposite format strategies — invisible on absolute counts, unmistakable on normalized bars. This is competitive intelligence in one glance: negotiate with each market according to what it actually produces.

\n

What happens if you skip it: On absolute bars, South Korea's 194 titles are a sliver next to the US block and its 78.4% TV skew — the single most actionable insight on the page — is literally invisible. The office concludes \"countries look about the same\" and licenses accordingly.

\n

Smart-work tip: Reach for the 100% variant whenever the comparison is about MIX across differently-sized groups (market shares, workforce composition, content strategy). Keep absolute counts in tooltips so a reader can still ask \"but how big was Korea?\" — hover answers 194.

\n

Reason: The genre bar is the payoff of the entire bridge-table architecture: a true ranking of INDIVIDUAL genres — impossible from the comma-joined strings — now falls out of one measure and one field. Smart-work tip: When a bar chart's values could be inflated by bridge-table grain, glance at one genre's number against expectations (Dramas ≈ 2,106 unique titles, not 2,900+ tags). A 10-second sanity check against a known title count catches grain bugs instantly.

8. Trainer's Troubleshooting: Common Beginner Mistakes

\n
\n Mistake 1 — Splitting listed_in into Columns instead of Rows: Splitting into Genre.1, Genre.2, Genre.3 makes it impossible to build a single clean Genre Bar Chart! Always split into Rows inside a separate Bridge Table.\n
\n
\n Mistake 2 — Counting rows of TitleGenres for Total Titles: That returns ~17,071 genre tags instead of 7,787 titles! Always use DISTINCTCOUNT('Titles'[show_id]).\n
