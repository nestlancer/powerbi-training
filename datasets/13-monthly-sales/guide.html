Four Real-World E-Commerce Export Traps Hidden in data/:
1. 545 Blank Rows + 355 Mid-File Repeated Headers: Several rows literally say Order ID, Product, Quantity Ordered... right in the middle of a month! If you don't filter Order ID <> \"Order ID\" and <> \"\" BEFORE converting types, Power Query throws 355 DataFormat.Errors!
2. The Two-Portlands Trap: Purchase Address (\"917 1st St, Dallas, TX 75001\") serves both Portland, OR ($1,870,732) and Portland, ME ($449,758)! Always build Market = City & \", \" & State so the two Portlands stay separate!
3. Midnight New Year Spillover: Sales_December_2019.csv contains 34 orders placed just after midnight on 01/01/20 ($8,670.29). All clean rows = $34,492,035.97; strict 2019 = $34,483,365.68.
4. Order Line vs. Basket Order ID: 185,950 line items belong to 178,437 distinct Order IDs (multi-item baskets like iPhone + Lightning Cable!). Always compute AOV using DISTINCTCOUNT('Sales'[Order ID])!

4. Phase A — Step-by-Step in Microsoft Excel (Power Query in Excel!)

Step A1 — Why You Should Use Excel's Built-In Folder Connector (Not Manual Copy-Paste)

185,950 rows easily fit inside Excel's 1,048,576-row grid, and Excel has the exact same Power Query engine as Power BI!
Click Data → Get Data → From File → From Folder → browse to datasets/13-monthly-sales/data → click Combine → Combine & Transform Data → click OK.
💡 Why do we do this?

Reason: When data arrives as many same-structured files (one per month, per region, per store), the Folder connector replaces copy-paste with automation: it stacks every CSV in the folder into one table, records the recipe, and — the crucial part — will pick up NEXT month's file automatically on Refresh. You're not combining 12 files once; you're building a pipeline that keeps combining them forever.

Real-time example: This is exactly the client's situation: \"every month our POS dumps a separate CSV into a shared folder.\" The old workflow: an analyst opens 12 files, copies each range, pastes into a master sheet, misses a row somewhere — 45 error-prone minutes monthly. The Folder workflow: one connection, defined once; January 2020 arrives as a 13th CSV and the whole dashboard updates in a 10-second refresh, no human touching the data. That difference is the entire ROI of learning Power Query.

What happens if you skip it: Manual stacks drift out of sync (a month forgotten, a paste misaligned), and the \"automate it!\" requirement in the brief goes unmet — the dashboard becomes a January-only artifact.

Smart-work tip: Whenever files share identical structure, never merge by hand — point a Folder (or SharePoint/SharePoint-folder in real jobs) connector at the directory. One connection to rule them all; new files join themselves.

💡 Why do we do this?

Reason: This step's hidden lesson is order of operations. The 12 monthly CSVs each contain 30-ish repeated header rows buried mid-file (someone concatenated files badly upstream), plus 545 blanks. If Power Query's auto-generated Changed Type step runs FIRST, it tries to type the literal text \"Order ID\" as a number and produces 355 DataFormat.Error cells — the scary red error state beginners panic over. Filter the text junk BEFORE typing columns, and no error ever appears. The PivotTable and Matrix independently verify the $34,492,035.97 total and 185,950 row count across all markets and hours.

Real-time example: Watch the two sequences on the same file: (A) auto-type first → 355 Errors → confused manual \"Replace Errors\" patching → junk rows still pollute totals; (B) filter Order ID ≠ \"Order ID\", ≠ null first → 900 junk rows gone in one click → types apply cleanly → 185,950 verified rows → pivot confirms $34,492,035.97. Same data, same tools — sequence (B) is 10 minutes, sequence (A) is a lost afternoon. LineRevenue meanwhile pre-builds the additive currency column that every later chart uses. The PivotTable and Matrix cross-check the $34,492,035.97 total and 185,950 rows.

What happens if you skip it: Error cells (Mistake 1), inflated totals that quietly include header rows as \"products\", and a pivot that won't reconcile to the checkpoint value.

Smart-work tip: Memorize the mantra: filter junk → fix types → compute columns. And treat Power Query errors as information, not enemies — an Error cell always means \"a step ran before its prerequisites were ready.\" The PivotTable and Matrix are the cheap insurance that stops nonsense from ever reaching a chart.

5. Phase B — Complete Power BI Folder Pipeline & Charts Journey

Stage 1 & 2 — Folder Combine, Junk Removal & Address Splitting in Power Query

  1. Click Home → Get data → More… → Folder → Connect → select datasets/13-monthly-sales/data → click Combine & Transform Data → click OK. Rename the combined query to Sales.
  2. CRITICAL ORDER OF OPERATIONS: Look at Applied Steps on the right: if Power Query auto-inserted a Changed Type step that already turned repeated \"Order ID\" rows into Error, click the X next to Changed Type first!
  3. Click the filter arrow on Order ID → uncheck null, (blank), and Order ID → click OK. All 900 junk rows vanish cleanly!
  4. Now set Data Types: Order ID = Text, Quantity Ordered = Whole Number, Price Each = Fixed decimal number ($).
  5. Parse Order Date (MM/DD/YY HH:MM): Right-click Order Date → Change Type → Using Locale → Data Type: Date/Time, Locale: English (United States). Then select Order Date → Add Column → Date → Date Only (OrderDate) and Add Column → Time → Hour → Hour (OrderHour, 0–23).
  6. Parse Purchase Address (Solve the Two-Portlands Trap!):
    • Select Purchase Address → Transform → Split Column → By Delimiter → Comma (Each occurrence) → produces 3 columns: Street, City, and StateZip (e.g. \" TX 75001\").
    • Select City and StateZip → Transform → Format → Trim.
    • Select StateZip → Transform → Split Column → By Delimiter → Space → rename to State and PostalCode (Text!).
    • Click Add Column → Custom Column → Name: Market → Formula: [City] & \", \" & [State]!
  7. Remove helper column Source.Name if not needed, then click Home → Close & Apply (confirm 185,950 rows!).
💡 Why do we do this?

Reason: The address parse exists because of the dataset's most famous trap: two different cities named Portland — Portland, OR ($1.87M) and Portland, ME ($449K). \"City\" alone merges them into a fake $2.32M \"Portland\" market, double the truth and wrong twice. The composite Market = City & \", \" & State makes geography unambiguous. The locale-parse of Order Date and the Hour extraction similarly convert text timestamps into the time dimensions every chart needs.

Real-time example: The business cost of the trap: a growth manager reading a city-only report concludes \"Portland is our #6 market, worth $2.3M — let's open a pop-up store there.\" But the revenue lives 3,000 km apart in two states; the real decision (which Portland?) can't even be asked. The same disambiguation logic applies far beyond this file: Paris, TX vs Paris, France; Springfield ×4 in Illinois alone; Cambridge, MA vs Cambridge, UK. Any city-level analysis without state/country context is one collision away from a wrong decision.

What happens if you skip it: Markets merge wrongly, the 10-market bar chart shows 9 markets (or two phantom \"Portlands\" mixed), and the ZIP becomes a number losing East Coast leading zeros.

Smart-work tip: When a free-text address field exists, ALWAYS build an unambiguous geographic key (City, State / City, Country) before charting geography. And keep ZIP as Text — it's an identifier, not a quantity (the Set 04 rule, still true).

Stage 3 & 4 — Calendar Table & E-Commerce DAX Measures

Calendar =
VAR Base = CALENDAR ( DATE ( 2019, 1, 1 ), DATE ( 2020, 1, 1 ) )
RETURN
ADDCOLUMNS (
    Base,
    "Year", YEAR ( [Date] ),
    "MonthNum", MONTH ( [Date] ),
    "MonthShort", FORMAT ( [Date], "MMM" ),
    "YearMonth", FORMAT ( [Date], "YYYY-MM" )
)
💡 Why do we do this?

Reason: A dedicated CALENDAR() table is the DAX-native way to guarantee a CONTIGUOUS date dimension — every day present, even days with zero sales — which time-intelligence functions require and a raw fact-table date column can't promise. ADDCOLUMNS then manufactures the slicer-friendly fields (Year, MonthNum, MonthShort, YearMonth), and relating + Mark as date table + sorting MonthShort by MonthNum finishes the setup the same way as Sets 03 and 18.

Real-time example: This dataset's own edge case proves the need: 34 orders dated Jan 1, 2020 spill into the file (that's why total revenue $34,492,035.97 vs strict-2019 $34,483,365.68 differ by $8,670.29). A calendar spanning 2019-01-01 → 2020-01-01 keeps those orders visible and attributable, so the December peak card ($4,613,443.34) and the monthly trend line read truthfully — and if you filter to 2019 you can SEE what the spillover was instead of silently losing it.

What happens if you skip it: SAMEPERIODLASTYEAR and any YTD pattern refuse to work (no marked date table), month axes sort Apr–Aug–Dec alphabetically, and the 2020 spillover either vanishes or contaminates the 2019 story unnoticed.

Smart-work tip: CALENDAR + ADDCOLUMNS is the universal date-table recipe — memorize it once and reuse it in every model. Always Mark as Date Table immediately, always sort month names by month numbers, and always check the calendar's span against the data's earliest/latest dates.

Relate Calendar[Date] (1) → (*) Sales[OrderDate], mark as Date table, and sort MonthShort by MonthNum. Then write:

Total Revenue =
SUMX ( 'Sales', 'Sales'[Quantity Ordered] * 'Sales'[Price Each] )
// Check: $34,492,035.97 (2019 only = $34,483,365.68)

Total Units = SUM ( 'Sales'[Quantity Ordered] )
// Check: 209,079

Distinct Orders = DISTINCTCOUNT ( 'Sales'[Order ID] )
// Check: 178,437

Avg Order Value (AOV) = DIVIDE ( [Total Revenue], [Distinct Orders] )
// Check: $193.30

Items per Basket = DIVIDE ( [Total Units], [Distinct Orders] )
// Check: 1.17 units/order
💡 Why do we do this?

Reason: These measures are a lesson in grain-aware ratios. The table's grain is the ORDER LINE (185,950 rows), but the business unit everyone quotes is the ORDER (178,437 baskets) — so Average Order Value must divide revenue by DISTINCTCOUNT(Order ID), never by COUNTROWS. Use the wrong denominator and you compute the \"average line value\" ($185.49) while believing it's AOV ($193.30) — a 4% understatement that compounds across every revenue projection built on it.

Real-time example: See the grain in action: one customer buys an iPhone + Lightning Cable in a single order — that's 1 order, 2 lines. Multiply that by 7,136 multi-item baskets and the two grains diverge by 7,513 rows. The Items per Basket = 1.17 measure then quantifies cross-selling success: every 0.01 rise means thousands more customers adding a second item (and the stretch challenge finds the #1 pair — iPhone + its cable, obviously). Revenue itself uses SUMX over line-level multiplication, because revenue lives at line grain but must aggregate to every level above it.

What happens if you skip it: Mistake 2 ships a wrong AOV into the deck; marketing ROI calculations keyed to AOV inherit the error; and \"how many baskets?\" questions get answered with line counts.

Smart-work tip: For any ratio, write the fraction out loud — \"revenue per WHAT?\" — before writing DAX. If the denominator is an entity (order, customer, session), it's a DISTINCTCOUNT; if it's a row, COUNTROWS. The 3-second habit prevents the most common ratio bug in e-commerce analytics.

💡 Why do we do this?

Reason: This is the chart that justifies the Hour column from Stage 2: ad platforms charge real money per impression, and impressions cost MORE at high-demand hours — so knowing WHEN this store's customers actually buy turns ad scheduling from guesswork into arbitrage. The hourly curve is the direct answer to the brief's \"best hours to run Facebook/Google ads.\"

Real-time example: The curve shows two demand humps: 12:00 (12,587 orders — lunch-scroll purchases) and 19:00 (12,905 orders — the evening couch-shopping peak), with the 3:00 AM trough at a fraction of those. The marketing translation: front-load daily budgets into 11:00–13:00 and 18:00–20:00 windows and ease off overnight, when the same ad dollars buy impressions shown to people who aren't buying. A team that shifts even 20% of spend from dead hours to the twin peaks buys the same order volume for less — measurable in the very next month's blended CAC.

What happens if you skip it: Ads run on flat 24-hour schedules, paying peak-impression prices through the 3am trough, and the \"why is our ROAS low?\" question never gets its answer — which was sitting in an Hour column all along.

Smart-work tip: Behavioral rhythms (hour-of-day, day-of-week) are the cheapest actionable analytics: one column + one line chart → a budget rule. Always convert such findings into a RECOMMENDATION sentence with numbers, exactly like this step does — that's what makes analysis operational.

Visual 4 High-Ticket Heroes vs. Basket Add-Ons — Dual-Axis Combo Chart

X-axisSales[Product]

Instant Insight: Macbook Pro Laptop drives $8,037,600 on just 4,728 units ($1,700 each), whereas AAA Batteries (4-pack) sells 31,017 packs ($2.99 each = $92.7K) — cheap consumables act as traffic & checkout add-ons!

💡 Why do we do this?

Reason: This chart answers the client's final question — \"why does our #1 unit seller make tiny revenue?\" — which is fundamentally a two-scale problem: revenue (millions) and units (tens of thousands) need separate axes, and a single-metric product ranking silently hides one of the two stories. The dual-axis combo lets each product be read on BOTH dimensions at once, exposing the strategic split between margin engines and traffic engines.

Real-time example: Read the four quadrants of product personality the chart reveals: Macbook Pro = high revenue / low units (the margin hero — 4,728 sales produce $8.04M); AAA Batteries = low revenue / massive units (31,017 packs = the traffic magnet and checkout add-on — the answer to the brief's puzzle); and products like iPhones sit in the middle. The merchandising consequence: batteries belong at checkout and in bundles (\"add batteries to your iPhone order\"), Macbooks deserve homepage hero placement — two different plays from one chart. It also explains why \"best seller by units\" and \"best seller by revenue\" are DIFFERENT products, a distinction casual dashboards routinely blur.

What happens if you skip it: The team celebrates AAA batteries as \"our top product\" (units) while the Macbook — 87× the revenue — gets no visibility; or conversely, the cheap add-on workhorse gets cut from the catalog for \"low revenue\", and average basket size (1.17) quietly drops.

Smart-work tip: For any catalog/portfolio question, force yourself to look at TWO measures — dollars AND volume — before ranking anything. Products, like employees, have roles: some earn, some attract. One combo chart shows who plays which position.

8. Trainer's Troubleshooting: Common Beginner Mistakes

Mistake 1 — Leaving Power Query's auto-Changed Type step BEFORE filtering out \"Order ID\": That turns 355 repeated headers into row errors! Always filter text junk BEFORE changing types.
Mistake 2 — Dividing Revenue by COUNTROWS('Sales') instead of DISTINCTCOUNT('Sales'[Order ID]): That gives $185.49 (Average Line Value) instead of the true $193.30 Average Order Value!
