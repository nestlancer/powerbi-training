4. Phase A — Step-by-Step in Microsoft Excel (Beginner Friendly)

Before opening Power BI, every strong analyst inspects the raw file in Excel, fixes obvious header bugs, and proves the grand totals with a PivotTable so you know your target numbers are rock solid.

Step A1 — Open the Raw File & Inspect the Excel Table

  1. Open Excel → click File → Open → Browse → navigate to datasets/01-financial-sample/data/Financial-Sample.xlsx.
  2. Click anywhere inside the data (for example cell A2). Look at the top ribbon: a green Table Design tab appears! Click Table Design and look at the far-left Table Name box — it says financials. That means rows 1 to 701 are already an official Excel Table.
  3. Click View → Freeze Panes → Freeze Top Row so row 1 stays visible when you scroll down to row 701.
💡 Why do we do this?

Reason: Professional rule #1 — understand the data before writing a single formula. Spotting the financials Excel Table tells you the range is "smart" (it auto-expands and auto-fills formulas), and freezing the header row stops you from misreading columns when you scroll deep into the data.

Real-time example: Imagine a store manager who receives this workbook every month. This month it has 700 rows; next month 740 rows arrive. If you had built formulas on a fixed range like A2:P701, the 40 new rows would be silently ignored — your totals would be wrong and nobody would notice. Because the data is a named Table, formulas and PivotTables stretch automatically. That is why we check Table Design → Table Name first, not last.

What happens if you skip it: Without frozen headers you will read column L (Profit) as column K (COGS) at row 400 and build the whole analysis on the wrong field. Fixing that later costs hours; checking now costs 20 seconds.

Smart-work tip: Make "open → inspect → freeze" a 2-minute ritual on EVERY new file. Hard workers start typing formulas immediately; smart workers understand the shape of the data first.

Step A2 — Fix the Hidden Header Space & Format Numbers

  1. Click cell J1 and look in the Formula Bar at the top. You will see  Sales (there is an invisible space before the S!). Double-click J1, delete everything, type Net Sales (clean and unambiguous), and press Enter.
  2. Check formats: Select columns H:L (click column letter H, hold Shift, click L) → Home → Number dropdown → Currency (or format $#,##0.00).
  3. Select column M (Date) → Home → Number dropdown → Short Date so dates read clearly (9/1/2013 or 2013-09-01).
  4. Check for missing cells: Press Ctrl + Shift + L (or click the filter arrows already on row 1). Click the dropdown arrow on Country, Segment, and Profit — scroll to the bottom of each filter list to verify there is no (Blanks) item.
💡 Why do we do this?

Reason: An invisible leading space makes the header " Sales" a different piece of text than "Sales". Excel, Power Query, and DAX all compare text character-by-character — a space is a real character — so every formula that refers to "Sales" by name will fail or silently pick the wrong column. Formatting currency and dates does not change the values, but it changes whether a human can verify them at a glance.

Real-time example: A colleague sends you a workbook where =MATCH("Sales", $A$1:$P$1, 0) returns #N/A even though a "Sales" column visibly exists. The cause? The real header was " Sales" with a space — the header text did not match. (VLOOKUP-style lookups that match on header names hit the same wall.) The same trap breaks SUMIFS, PivotTables that show "Sum of  Sales", and SQL imports that create a column literally named Sales . Prove it to yourself: click an empty cell, type =LEN(J1) — it returns 6 (1 space + 5 letters) instead of 5. That is forensic-level proof in 3 seconds.

What happens if you skip it: You carry the dirty header into Power BI, where you must reference 'Financials'[ Sales] in every measure — ugly, fragile, and confusing for teammates. Unformatted numbers like 118726350.26 also make verification slow and error-prone.

Smart-work tip: Always check headers with the Formula Bar, not the grid — the grid hides the space, the Formula Bar reveals it. Renaming to Net Sales also makes the column self-documenting (Net = after discounts).

Step A3 — Add 3 Beginner Helper Columns (Columns Q, R, S)

Because the data is already an Excel Table (financials), when you type a header in Q1, Excel automatically expands the table and fills your formula down all 700 rows!

  1. Click cell Q1, type RowMarginPct, and press Enter. In cell Q2, type:
    =IF(J2=0, 0, L2/J2)
    Plain-English meaning: Divide Profit (L2) by Net Sales (J2), returning 0 if sales were ever zero. You'll see: Q2 first displays something like $50.00 — Excel auto-copies the currency format of the columns you divided (row 2: $16,185 ÷ $32,370 = 0.5). That is auto-formatting, not a mistake! Select column Q → click the % button on the Home tab and click Increase Decimal once (0.0%) → Q2 reads 50.0%.
  2. Click cell R1, type ProfitStatus, and press Enter. In cell R2, type:
    =IF(L2<0, "Loss", IF(L2=0, "Break-Even", "Profitable"))
    You'll see: R2 shows the text Profitable immediately (row 2's Profit is positive) — text results never pick up a number format, so nothing to fix. Check it: Click the filter arrow on ProfitStatus → filter to Loss → look at the bottom-left Excel status bar: it says 58 of 700 records found! Click Data → Clear so no filter stays active!
  3. Click cell S1, type BandSort, and press Enter (this teaches you how to sort text bands in logical order instead of alphabetical!). In cell S2, type:
    =IF(D2="None", 1, IF(D2="Low", 2, IF(D2="Medium", 3, 4)))
    You'll see: S2 shows the plain number 1 (row 2's Discount Band is None) — deliberately left unformatted, so the codes 1–4 sort in logical order.

Note: If Excel turned your formula into structured table syntax like =IF([@[Net Sales]]=0,0,[@Profit]/[@[Net Sales]]), that is completely normal inside an Excel Table — both formulas give the exact same result!

💡 Why do we do this?

Reason: Helper columns convert raw numbers into decisions. RowMarginPct tells you if an individual deal is healthy, ProfitStatus turns 700 rows into three filterable buckets (Profitable / Break-Even / Loss), and BandSort forces text tiers into a logical order. You are not changing the data — you are adding the business logic that questions will be asked against.

Real-time example: In a review meeting the CFO asks: "How many individual deals lost money last year?" Without ProfitStatus, you would scan 700 cells of red-and-green numbers or improvise a COUNTIF under pressure. With it, one filter click answers instantly: 58 loss rows. Same story with BandSort: text sorts alphabetically by default, so Discount Band lines up as High → Low → Medium → None — a zigzag that hides the beautiful margin staircase (21.9% → 17.9% → 14.4% → 9.1%). The sort column fixes the story before the chart is even drawn.

What happens if you skip it: Every future analysis re-invents the same logic by hand, and charts get presented with alphabetically-sorted nonsense that confuses stakeholders. Also notice the IF(J2=0,0,...) guard — without it, a zero-sales row would return #DIV/0! and poison every total it touches.

Smart-work tip: Build the logic ONCE as a column and reuse it forever. Inside an Excel Table, typing the formula in row 2 auto-fills all 700 rows and every future row — that is the "smart work" the Table gives you for free.

Step A4 — Prove the Numbers with Two Quick PivotTables

  1. Click any cell inside the table → click Insert → PivotTable → leave New Worksheet selected → click OK.
  2. Double-click the new sheet tab at the bottom and rename it Pivot_Check.
  3. In the PivotTable Fields pane on the right:
    • Drag Country into Rows.
    • Drag Net Sales into Values, and drag Profit into Values.
    • Right-click any number in Sum of Net Sales → Number Format → Currency → 2 decimals → OK. Do the same for Sum of Profit.
    • Right-click any number in Sum of Profit → Sort → Sort Largest to Smallest.
  4. Verify against Section 1: Confirm Grand Total Net Sales = $118,726,350.26, Grand Total Profit = $16,893,702.26, France is #1 in Profit ($3,781,020.78), and USA is #1 in Net Sales ($25,029,830.17).
  5. Now test Segment: drag Country out of Rows and drag Segment into Rows. Confirm Enterprise shows -$614,545.62!
💡 Why do we do this?

Reason: Golden audit rule — know your target numbers BEFORE building the dashboard. A PivotTable computes totals through a completely different engine than Power BI. If both engines agree, your data is clean; if they disagree, you have a bug to find — and you want to find it now, not during a client demo.

Real-time example: Later in Power BI, your Net Sales card will show $118.73M. Because your PivotTable Grand Total already said $118,726,350.26, you can trust that number and move on. And when a stakeholder challenges you — "Why do you claim France out-earns the USA?" — you answer instantly with verified figures: France profit $3,781,020.78 vs USA $2,995,540.66, because USA discounts $2.24M away. Confidence like that only comes from independent verification.

What happens if you skip it: You present the dashboard, someone opens the raw file in Excel, the numbers don't match (for example, because the dataset got double-loaded — 1,400 rows instead of 700), and your credibility takes a hit that no pretty chart can repair.

Smart-work tip: Screenshot the verified PivotTable and keep it beside you as your dashboard's acceptance test. Professional testers call this a "golden dataset" — you are doing real QA, not just clicking buttons.

Step A5 — Save Your Clean Workbook

Click back to Sheet1, double-check that no filter is active (all 700 rows visible), then click File → Save As and save as 01-financial-sample-clean.xlsx inside the 01-financial-sample folder.
💡 Why do we do this?

Reason: Never mutate the raw source — keep the original untouched and save your work as a separate "clean" copy. This is the simplest possible version of the data-engineering pattern of raw (immutable) vs. cleaned (derived) layers, and it guarantees you can always start over.

Real-time example: Real data teams store raw files as read-only "source of truth". Six months from now, a colleague overwrites a formula or Power BI refresh misbehaves — if the raw file is still pristine, you re-derive the clean workbook in 5 minutes. If you saved over the original, your only options are undo-history archaeology or rebuilding from scratch.

What happens if you skip it: One accidental Ctrl+S on a filter-active sheet hides 642 of your 700 rows from every downstream PivotTable, and you no longer have the true source to compare against. Also, a hidden filter quietly drops rows from pivots — totals shrink with no error message.

Smart-work tip: Use a naming convention that mirrors the project (01-financial-sample-clean.xlsx lives in 01-financial-sample/). Future-you — and every teammate — can find the right file in seconds without opening anything.

5. Phase B — Complete Power BI & Charts Journey (Step-by-Step)

You can connect Power BI either to your cleaned 01-financial-sample-clean.xlsx OR directly to the raw data/Financial-Sample.xlsx (below we show how to clean the raw file right inside Power Query so you learn the repeatable developer workflow!).

Stage 1 — Connect to Data (Avoid the Navigator Duplicate Trap!)

  1. Open Power BI Desktop → close the splash screen → on the Home ribbon click Excel workbook (or Get data → Excel workbook).
  2. Select data/Financial-Sample.xlsx (or your 01-financial-sample-clean.xlsx) and click Open.
  3. CRITICAL BEGINNER CHECK in the Navigator window: You will see TWO items:
    • financials (has a blue bar on top = official Excel Table) ✅ Tick ONLY this box!
    • Sheet1 (plain grid icon = worksheet) ❌ Leave UNTICKED! (If you tick both, you load the exact same 700 rows twice!)
  4. Click the Transform Data button at the bottom-right (NOT Load yet — always inspect in Power Query first!).
💡 Why do we do this?

Reason: The Navigator offers BOTH Sheet1 (the worksheet) and financials (the Excel Table sitting on top of that same worksheet). They are the same 700 rows wearing two outfits — loading both is like pasting the same photo into your album twice. And clicking Transform Data instead of Load means you inspect and clean the data BEFORE it ever enters the model, which is the professional ETL order: shape first, then load.

Real-time example: A junior analyst ticks both boxes because "more data can't hurt". Every total in the report doubles — Total Profit reads $33.79M instead of $16.89M — and nobody catches it until the CFO, who knows the business, says "our profit was not 33 million last year". That single checkbox costs the analyst their credibility for the whole project.

What happens if you skip it: Double-loaded rows corrupt every sum, average, and count (700 → 1,400 rows), and skipping Transform Data bakes dirty headers and wrong data types straight into the model — you end up patching in DAX what should have been fixed upstream in 30 seconds.

Smart-work tip: In the Navigator, the item with the blue bar and tiny table icon is the named Table — prefer it over the raw sheet, because named Tables keep working correctly when rows are added later. Ritual: tick one source, Transform Data, breathe.

Stage 2 — Clean & Shape in Power Query Editor

  1. Rename the Query: In the right-hand Query Settings → Properties → Name box, change financials to Financials (clean PascalCase table name).
  2. Fix the Hidden Header Space (if reading raw file): Scroll across to the  Sales column. Double-click the header, type Net Sales, and press Enter.
  3. Trim Text Columns (Good Habit): Hold Ctrl and click the headers Segment, Country, Product, and Discount Band → go to the Transform tab → click Format → Trim.
  4. Verify Data Types (click the small icon on the left of each column header):
    • Segment, Country, Product, Discount Band, Month Name → ABC (Text)
    • Units Sold → 1.2 (Decimal Number) — do NOT choose Whole Number, or half-units like 1618.5 get rounded!
    • Manufacturing Price, Sale Price, Gross Sales, Discounts, Net Sales, COGS, Profit → $ (Fixed decimal number / Currency) or 1.2 (Decimal Number)
    • Date → Calendar icon (Date) — if it says Date/Time, click it and choose Date.
  5. Add the Discount Band Sort Column (in Power Query): Click the Add Column tab → Conditional Column:
    • New column name: BandSort
    • If Discount Band equals None → Output 1
    • Click Add Clause: Else If Discount Band equals Low → Output 2
    • Click Add Clause: Else If Discount Band equals Medium → Output 3
    • Else → 4 → click OK. Change BandSort's type icon to 123 (Whole Number).
  6. Look at Applied Steps on the right — every transformation is recorded! Click Home → Close & Apply.
💡 Why do we do this?

Reason: Power Query is a recipe recorder, not a one-time cleanup. Every click (rename, trim, data type, conditional column) is saved as an Applied Step, so the identical cleaning replays automatically on every refresh. You are not "fixing a file" — you are teaching Power BI a repeatable process.

Real-time example: Two analysts get next month's file. Analyst A cleaned last month's data by hand in Excel: 2 hours of retyping, and one column forgotten. Analyst B cleaned in Power Query: one click on Refresh, 30 seconds, every step re-applied — header renamed, text trimmed, types set, BandSort rebuilt. That is the entire business case for Power Query, and it's why 90% of a real developer's time is spent in this editor.

What happens if you skip it: Invisible trailing spaces survive into the model, so slicers show twins like Canada and Canada  as two separate filter items, splitting the country's sales in half. Wrong data types (Decimal → Whole Number) quietly round 1618.5 units to 1619 — small per row, wrong in every total.

Smart-work tip: Rename the query to clean PascalCase (Financials) — every future DAX formula reads like English: 'Financials'[Net Sales]. And glance at Applied Steps before closing; each step should have a reason you can say out loud.

Stage 3 — Data Modeling, Date Table & Custom Sorting

Even on a 1-table workbook, professional Power BI developers create a continuous Calendar Date Table so DAX Time Intelligence (SAMEPERIODLASTYEAR, TOTALYTD) works without gaps.

  1. Click Data view (table icon on the left rail) → on the top Table tools ribbon click New table → paste this DAX formula and press Enter: 
    Calendar =
ADDCOLUMNS (
    CALENDAR ( DATE ( 2013, 1, 1 ), DATE ( 2014, 12, 31 ) ),
    "Year", YEAR ( [Date] ),
    "MonthNum", MONTH ( [Date] ),
    "Month", FORMAT ( [Date], "MMM" ),
    "YearMonth", FORMAT ( [Date], "YYYY-MM" ),
    "Quarter", "Q" & FORMAT ( [Date], "Q" )
)
  2. Mark as Date Table: With Calendar selected, click Table tools → Mark as date table → Mark as date table → choose column Date → click OK.
  3. Fix Alphabetical Month Sorting: In Calendar, click the Month column → click Column tools → Sort by column → MonthNum. (Now charts run Jan, Feb, Mar... instead of Apr, Aug, Dec...!)
  4. Fix Alphabetical Discount Band Sorting: Click the Financials table on the right → click the Discount Band column → click Column tools → Sort by column → BandSort.
  5. Set Country Geography: Click Financials[Country] → Column tools → Data category → Country.
  6. Create the Relationship: Click Model view (3rd icon on the left rail). Drag Calendar[Date] onto Financials[Date]. Confirm the line shows 1 on Calendar and * (many) on Financials.
  7. Hide Clutter Columns: In Model view, click the eye icon to hide Financials[Date], Financials[Month Number], Financials[Month Name], Financials[Year], Financials[BandSort], and Calendar[MonthNum] so you never accidentally drag the wrong Year or Month onto a chart!
💡 Why do we do this?

Reason: Three hidden laws of modeling live in this stage. (1) Time intelligence needs a continuous calendar — SAMEPERIODLASTYEAR walks day-by-day through a date table, so gaps or missing years make YoY measures return blanks. (2) Text sorts alphabetically, always — months line up Apr-Aug-Dec unless you attach a numeric sort column. (3) Relationships decide how filters flow — one Calendar date filters many fact rows (1-to-many), which is what lets one slicer move every visual on the page.

Real-time example: Your fact table only stores 16 dates (the 1st of each month, Sep 2013 – Dec 2014). Ask for "Profit in November 2013" and Power BI finds the date; ask SAMEPERIODLASTYEAR for Sep–Dec 2014 and it must walk back through a full 2013 calendar — which only exists if your Calendar table spans 2013-01-01 to 2014-12-31, even for months with no sales. Skipping the Calendar table here is the single most common reason beginners see a blank YoY card and conclude "DAX is broken".

What happens if you skip it: The combo chart reads Apr, Aug, Dec, Feb... (alphabetical!) and the Discount Band chart reads High, Low, Medium, None — both hide the true staircase pattern. Unhidden duplicate date columns mean you might drag Financials[Year] onto one visual and Calendar[Year] onto another, creating visuals that refuse to filter each other.

Smart-work tip: Mark as Date Table is your receipt — it tells Power BI "this is the official calendar", so every time-intelligence function uses it without guessing. Hiding helper columns is not cosmetic: it removes 6 wrong choices from the field list so the only remaining choice is the right one.

Stage 4 — DAX Measures (Beginner → Intermediate → Advanced)

Switch to Report view (top icon on left rail). Right-click the Financials table in the Data pane → click New measure for each formula below. After pressing Enter on each measure, set its format in the top Measure tools ribbon!

Beginner Measures (Core Additive Totals)

Gross Sales = SUM ( 'Financials'[Gross Sales] )
// Format: Currency ($), 2 decimals -> Check card: $127.93M ($127,931,598.50)

Total Discounts = SUM ( 'Financials'[Discounts] )
// Format: Currency ($), 2 decimals -> Check card: $9.21M ($9,205,248.24)

Net Sales = SUM ( 'Financials'[Net Sales] )
// Format: Currency ($), 2 decimals -> Check card: $118.73M ($118,726,350.26)

Total COGS = SUM ( 'Financials'[COGS] )
// Format: Currency ($), 2 decimals -> Check card: $101.83M ($101,832,648.00)

Total Profit = SUM ( 'Financials'[Profit] )
// Format: Currency ($), 2 decimals -> Check card: $16.89M ($16,893,702.26)

Units Sold Total = SUM ( 'Financials'[Units Sold] )
// Format: Whole number with comma (#,0) -> Check card: 1,125,806
💡 Why do we do this?

Reason: These five SUM measures are the P&L skeleton — and they're written as MEASURES, not calculated columns, because measures compute at query time and respect every slicer/filter automatically. Just as important as the formulas is the discipline of setting each measure's format string in the Measure tools ribbon immediately: a measure's formatting lives with the measure, so every card, axis, and tooltip inherits "$127.93M" instead of a raw 127931598.5.

Real-time example: The check-card values do free quality assurance: Gross $127.93M − Discounts $9.21M = Net $118.73M, and Net − COGS $101.83M = Profit $16.89M — the income statement ties out to the penny in four cards. Add Units (1,125,806) and you can quote $16.89M ÷ 1,125,806 ≈ $15.00 profit per unit in the same breath — an instant sanity metric a CFO recognizes. If any card disagrees with these figures, the model (not the business) is wrong — catch it now, not in the review.

What happens if you skip it: Unformatted measures render 16 decimal places or rounded integers in different visuals, and without the check-card discipline a silent filter error ships to the exec deck.

Smart-work tip: Write the expected value as a // Check comment the moment you author a measure — verification is part of writing the measure, not an afterthought. And default to measures over calculated columns for anything that aggregates: columns bloat the model, measures don't.

Intermediate Measures (Safe Ratios & Conditional Counts)

Net Margin % = DIVIDE ( [Total Profit], [Net Sales], 0 )
// Format: Percentage (%), 1 decimal -> Overall check: 14.2% (14.23%)
// WHY DIVIDE? Never average row-level margins! Always divide total profit by total net sales.

Discount Rate % = DIVIDE ( [Total Discounts], [Gross Sales], 0 )
// Format: Percentage (%), 1 decimal -> Overall check: 7.2% (7.20%)

Loss Rows Count = CALCULATE ( COUNTROWS ( 'Financials' ), 'Financials'[Profit] < 0 )
// Format: Whole number -> Overall check: 58
💡 Why do we do this?

Reason: This tier teaches the two rules that separate professional ratio work from spreadsheet errors. (1) Never average a ratio — divide the totals. Net Margin % divides total profit by total net sales; it does NOT average the 700 row-level margins, because an average weights a tiny row the same as a $20M segment. (2) DIVIDE's third argument guards division by zero, so a segment with no sales returns a clean blank instead of an error that blanks whole visuals.

Real-time example: Feel the wrongness concretely: overall margin is 14.2% ($16.89M ÷ $118.73M). But the 700 segment rows include deep losers and a few high-margin niches — averaging their margins produces a different number that no reconciliation supports, yet it LOOKS plausible on a card. Meanwhile Loss Rows Count = 58 reveals the portfolio shape: 642 segments make money, 58 bleed — and a later visual can isolate those 58 to ask WHERE the losses concentrate. That's the analyst's reflex: counts for scale, ratios for quality, never mixed up.

What happens if you skip it: Average-of-margins cards that match nothing, and #DIV/0!-style blanks when a slicer isolates a zero-revenue segment, taking whole report pages blank with them.

Smart-work tip: Make DIVIDE your default for every ratio and build conditional counts (CALCULATE + COUNTROWS + filter) as named measures — they become the building blocks of gauges, KPIs, and conditional formatting in every later set (the 11.70%-yes funnel, the 22.12% default rate — same skeleton).

Advanced Measures (Time Intelligence YoY % & Share of Profit)

Profit PY = CALCULATE ( [Total Profit], SAMEPERIODLASTYEAR ( 'Calendar'[Date] ) )
// Format: Currency ($) -> When filtered to Year = 2014 & Months Sep-Dec, returns $3,878,464.51!

Profit YoY % =
VAR PriorProfit = [Profit PY]
RETURN
    IF ( NOT ISBLANK ( PriorProfit ), DIVIDE ( [Total Profit] - PriorProfit, PriorProfit ) )
// Format: Percentage (%), 1 decimal -> For Sep-Dec 2014 vs Sep-Dec 2013, check: +40.1% (+40.15%)
💡 Why do we do this?

Reason: A measure is a single definition that Power BI recalculates inside every filter context — country, segment, month, discount band, whatever is selected. One formula, infinite correct answers. That is the difference between a model and a pile of numbers, and it is why professionals almost never sum in a visual directly.

Real-time example: The ONE measure [Net Margin %] = DIVIDE([Total Profit], [Net Sales]) correctly shows 14.2% overall, 15.5% for France, -3.1% for Enterprise, and 9.1% for High-discount rows — four different business answers from one formula, with zero extra work. Now the classic trap this file is famous for: if you instead wrote AVERAGE(RowMarginPct), you would get 27.9% — because tiny-but-73%-margin Channel Partner orders get the same vote as giant 10%-margin Small Business orders. Weighting every row equally when the dollars are unequal is the #1 margin lie in amateur dashboards.

What happens if you skip measures: Numbers get hardcoded or recomputed by hand for each view; two teammates produce two different "profit margins"; and the moment someone clicks a slicer, hardcoded values stop responding — the report lies silently.

Smart-work tip: Notice the pro habits baked into these formulas: DIVIDE instead of / (survives divide-by-zero), CALCULATE to override filter context for Prior Year, and IF(NOT ISBLANK(...)) so 2014-only months don't fake a +∞% YoY. After each measure, type its expected value from Section 1 into a card and check it — that is unit-testing, analyst style.

Real-time example: Trace the chart after building it: a tall column month where the gold margin line dips is a month the company bought revenue with discounts — sales went up, efficiency went down. Smart-work tip: Pull Calendar[Year] + Calendar[Month] into the X-axis and hit Expand all down one level so all 16 months appear in true calendar order — proof your Stage 3 sort work paid off. Reason: Slicers convert a static report into a conversation, and the What-If parameter converts a question into a live negotiation. This is the difference between reporting the past and supporting a decision about the future — the whole reason dashboards exist.

Real-time example: In the meeting, the sales VP asks: "What if we cap extra discounts at 5% to win more Enterprise deals?" The conclusion lands in the same breath as the question: a flat 5% giveaway destroys 38% of profit — maybe target discounts surgically instead.

What happens if you skip it: Every scenario becomes a new email request, the report goes stale within weeks, and you stay a "report builder" instead of becoming the analyst who runs the meeting.

Smart-work tip: Use the Sep–Dec 2014 slicer test ([Profit YoY %] = +40.15%) as your model's health check — if it stops matching, a relationship or filter broke. Add a Clear all slicers button top-right so executives can reset everything in one click; and always sanity-check that with no filters, the page totals exactly 700 rows.

8. Trainer's Troubleshooting: Mistakes That Trip Beginners

Mistake 1 — Totals are double ($33.79M Profit instead of $16.89M): You ticked BOTH financials and Sheet1 in Power BI Navigator. Open Transform data, right-click the extra Sheet1 query on the left, and click Delete.
Mistake 2 — Net Margin % shows 27.9% instead of 14.2%: You averaged the row-level margin column (AVERAGE(RowMarginPct)), giving tiny Channel Partner orders the same weight as massive Small Business orders! Always compute ratios with DIVIDE([Total Profit], [Net Sales]).
Mistake 3 — Full-year 2014 vs 2013 looks like +235% growth: Remember 2013 only contains 4 months (Sep–Dec), whereas 2014 has all 12 months! Always check date coverage before presenting annual growth to a CFO.
Mistake 4 — Discount Band or Months sort alphabetically: Select the text column in Data view → Column tools → Sort by column → pick its numeric sort column (BandSort or MonthNum).
