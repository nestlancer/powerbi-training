💡 Why do we do this?

Reason: A capstone opens with reconciliation for the same reason every enterprise report does: the PE board's turnaround thesis rests on numbers, so you prove the pipeline first — at 220,000 rows the Data Model PivotTable (not grid formulas) is the right tool, compressing and aggregating instantly where raw-grid pivots choke. Verifying three headline totals now means every Power BI page you build later must reproduce them or be rejected.

Real-time example: Notice what this one pivot already reveals BEFORE any BI work: $704.31M of sales produces just $18.71M profit — 2.66 cents on the dollar — and the damage is concentrated: Furniture loses −$13.26M, single-handedly erasing nearly half of Technology's +$31.70M gain. You walk into the model build already knowing the turnaround story lives in Furniture and discounting, not in celebrating growth. That's the analyst's edge: find the losses early.

What happens if you skip it: If your app's totals drift from these verified figures, the first board member with a calculator destroys trust in every other number on screen.

Smart-work tip: On any large audit, pivot the WORST categories first — the story is in the losses. And load >100K-row CSVs through the Data Model (or Power BI) as a habit; Excel grids stop being a professional tool around that size.

5. Phase B — Complete 3-Page Power BI Capstone Build

Stage 1 & 2 — Power Query Setup & Discount Banding

  1. Import data/retail_sales_2021_2024.csv → Transform Data → rename to RetailSales.
  2. Verify OrderDate & ShipDate = Date; Sales & Profit = Fixed decimal number ($); Discount = Decimal Number; Quantity = Whole Number.
  3. Add Custom Column ShipDays = Duration.Days([ShipDate] - [OrderDate]).
  4. Add ordered DiscountBand (0%, 1–15%, 16–25%, 26–35%, 36%+) + DiscountBandSort (1..5). Click Home → Close & Apply.
💡 Why do we do this?

Reason: Two prep moves make the capstone's central discovery measurable. Fixed-decimal money types keep a $704M total reconciling to the cent (the Set 18 typing law, now at retail scale). And the ordered DiscountBand converts a continuous 0–60% discount column into five ANALYZABLE bands with a sort column — the same banding pattern as Set 15's LeadTime bands, used whenever a policy boundary is the story. ShipDays adds the service-quality lens the Action Sheet will need later.

Real-time example: The "Discount Cliff" is literally invisible in the raw column: no single 40%-off row looks alarming. But once banded, the profit collapse marches down the ladder: +19.93% at 0% → +14.00% → +8.00% → +2.02% → −15.82% at 36%+. That monotone staircase IS the discount-policy story — and it only reads as a staircase because the bands are ordered (an alphabetical axis would show 0%, 16–25%, 1–15%... and destroy the narrative). Banding turns an arithmetic fact into a management conversation: "why are we allowing 36%+ discounts at all?"

What happens if you skip it: Without bands, the cliff hides inside averages (~24.1% mean discount tells you nothing); without the sort column, the axis scrambles; without ShipDays, delivery-performance questions die in Power Query.

Smart-work tip: Band any continuous risk variable (discount %, lead time, age, tenure) when a POLICY threshold is the point — the band edges become the policy dial the business can turn. Always pair band labels with a numeric sort column. The Power BI Matrix Visual mirrors the classification and cross-checks the totals.

Stage 3 & 4 — Calendar Table, Core DAX, Field Parameters & What-If Cap!

Build Calendar = CALENDAR(DATE(2021,1,1), DATE(2024,12,31)) with Year, Quarter, MonthNum, MonthShort, and relate Calendar[Date] (1) → (*) RetailSales[OrderDate] (plus inactive to ShipDate!). Write core measures:

Total Sales = SUM ( 'RetailSales'[Sales] )
// Check: $704,313,162.91

Total Profit = SUM ( 'RetailSales'[Profit] )
// Check: $18,710,044.29

Profit Margin % = DIVIDE ( [Total Profit], [Total Sales] )
// Format: 0.0% -> shows 2.7%, not the raw 0.0266
// Check: 2.66%

Total Units = SUM ( 'RetailSales'[Quantity] )
// Check: 1,648,536

Avg Discount % = AVERAGE ( 'RetailSales'[Discount] )
// Format: 0.0%

Sales YoY % =
VAR PY = CALCULATE ( [Total Sales], SAMEPERIODLASTYEAR ( 'Calendar'[Date] ) )
RETURN DIVIDE ( [Total Sales] - PY, PY )
// Format: 0.0%

// Recover Pre-Discount List Revenue & Implied Cost per Row for What-If Cap!
// Since Sales = ListRev * (1 - Discount) and Cost = Sales - Profit:
Simulated Profit (With Discount Cap) =
VAR Cap = 'Discount Cap'[Discount Cap Value]
RETURN
SUMX (
    'RetailSales',
    VAR d = 'RetailSales'[Discount]
    VAR s = 'RetailSales'[Sales]
    VAR p = 'RetailSales'[Profit]
    VAR Cost = s - p
    VAR ListSales = DIVIDE ( s, 1 - d, s )
    VAR NewDisc = MIN ( d, Cap )
    VAR NewSales = ListSales * ( 1 - NewDisc )
    RETURN NewSales - Cost
)

Profit Uplift from Cap = [Simulated Profit (With Discount Cap)] - [Total Profit]
💡 Why do we do this?

Reason: The calendar and core measures follow the course's standard skeleton (CALENDAR, YoY via SAMEPERIODLASTYEAR — nothing new). The capstone twist is the What-If simulator, and it works because of a per-row algebra trick: since Sales = ListRev × (1 − Discount), each row's pre-discount list price can be RECONSTRUCTED as ListRev = Sales ÷ (1 − Discount), with cost recovered as Sales − Profit. The SUMX then re-applies a CAPPED discount to every row and computes counterfactual profit — a scenario engine living inside the data model, respecting every slicer automatically.

Real-time example: The CEO's money question is "what if we capped rep discounts at 30%?" Slide the cap (Stage 4's parameter): every order above 30% re-prices down — including the 78,053 orders in the 36%+ band that are currently losing −$37.73M — and the Uplift card quantifies the rescue as a board-defensible number that updates live as you slice by region or rep. Without the row-level reconstruction there is no way to answer this: average discount can't be "re-applied" retroactively; you must go row by row.

What happens if you skip it: The discount recommendation stays a hand-wave ("deep discounts seem bad, maybe cap them?") instead of "capping at 30% recovers tens of millions, here's the exact number" — and policy debates never close.

Smart-work tip: Counterfactual DAX always follows this recipe: recover a known identity per row (here list price), hold COSTS fixed, vary the single POLICY variable via a parameter. Note also DIVIDE(s, 1-d, s)'s third argument guarding the 100%-discount edge case — defensive DIVIDE everywhere. The Power BI Matrix Visual mirrors the classification and cross-checks the totals.

Two Portfolio-Winning Modeling Clicks (Takes 60 Seconds Each!):
1. Create a Field Parameter (Dynamic Metric Switcher): Click Modeling → New parameter → Fields → Name: Metric Selector → drag in [Total Sales], [Total Profit], [Profit Margin %], and [Total Units] → click Create! Format the resulting slicer as horizontal Tile buttons!
2. Create the What-If Parameter (Discount Cap Slider): Click Modeling → New parameter → Numeric range → Name: Discount Cap, Data type: Decimal number, Minimum: 0.15, Maximum: 0.60, Increment: 0.05, Default: 0.30 → click Create!
💡 Why do we do this?

Reason: These two 60-second parameter clicks are what upgrade a static report into an APP — the capstone's whole thesis. A Field Parameter lets one visual morph across measures (Sales / Profit / Margin % / Units): one trend chart does the work of four, and the EXECUTIVE chooses the lens. A What-If Parameter materializes a hypothetical dial (0.15–0.60) as a real, selectable value that feeds the simulator measure — turning "what would happen if..." into an interactive control.

Real-time example: Picture the board meeting: someone squints at the trend line and asks "ok — but how does that look in units?" With the metric tiles you CLICK a button and the chart redraws instantly; without it you rebuild a chart live while the room watches. Then on Page 2, the Discount Cap slider becomes a negotiation table: slide from 25% to 35% and watch [Simulated Profit] and [Profit Uplift] reprice the policy in real time — the board converges on a number, not a feeling. Parameters encode the questions stakeholders actually ask.

What happens if you skip it: Four near-identical trend charts clutter Page 1, and the "policy lab" ships with one pre-baked scenario — the first follow-up question ("what about 25%? for APAC only?") exceeds what the report can answer.

Smart-work tip: Reach for a Field Parameter whenever stakeholders say "can I see this by X or Y?", and a What-If parameter whenever they say "what would happen if we changed X?" — these two clicks cover 80% of what makes users call a report "an app". The Power BI Matrix Visual mirrors the classification and cross-checks the totals.

Page 3 + Custom Tooltip Drill-Through Action Sheet & Hover Tooltip Page

1. Drill-Through Page (`Action Sheet`): Drag SubCategory and Region into the Drill through well at the bottom of Visualizations! Power BI auto-adds a Back button (`Ctrl+Click` in Desktop). Add a conditional-formatted Table of ProductName, CustomerSegment, ShipMode, [Total Sales], [Avg Discount %], and [Total Profit].
2. Custom Tooltip Page: Add a tiny hidden page (`Format Page → Page information → Allow use as tooltip = On`, Canvas size = `Tooltip`) showing a mini Category Profit Bar whenever an executive hovers over any Region or Month on Page 1!

💡 Why do we do this?

Reason: Pages 1–2 answer "what is wrong and what if?" — Page 3 answers "so what: WHO exactly do we fix?" Drill-through turns every visual into a doorway: right-click the Furniture bar → drill through → land on a filtered Action Sheet listing the losing products, customers, and ship modes BEHIND that bar. The custom tooltip page works the other direction: it injects micro-context INTO hover, so executives get detail without ever leaving their current page.

Real-time example: Follow the capstone's closing argument: a VP hovers over the APAC bar and a mini profit-by-category chart appears in place (Furniture red even there); then right-clicks Furniture → the Action Sheet reveals the actual −$3M products and the 36%+ discount customers behind them — the meeting ends with NAMED accounts and products on the fix list. That's the difference between a report and a turnaround instrument. (And hide the helper tabs — Mistake 2 — so the app opens clean on Page 1.)

What happens if you skip it: Finding "why does Tables lose $3.28M?" requires screenshots, filters, and manual digging — the app's "action sheet" promise becomes a promise of more analyst hours instead of self-service.

Smart-work tip: The professional 3-page anatomy — Overview (what), Lab (why/what-if), Action sheet (who) — generalizes to any portfolio app. Tooltips add context IN PLACE; drill-through adds depth ON DEMAND; hide helper pages so users enter only through the front door. The Power BI Matrix Visual mirrors the classification and cross-checks the totals.
