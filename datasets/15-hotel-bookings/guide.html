1. Literal "NA" & "NULL" Strings: Column children has 4 literal "NA" strings (replace with 0 before converting to Whole Number!), and country / agent / company store literal "NULL" strings.

4. Phase A — Step-by-Step in Microsoft Excel

Step A1 — Import & Reconstruct Arrival Date + Room Revenue

Load datasets/15-hotel-bookings/data/hotels.csv via Data → From Text/CSV. Add 3 helper columns:
• AG2 (ArrivalDate): =DATEVALUE(G2 & "-" & E2 & "-" & D2) (format as yyyy-mm-dd)
• AH2 (TotalNights): =H2+I2
• AI2 (RoomRevenue): =AH2*AB2 (where AB is adr)
Verify with SUMIFS: is_canceled = 0 Realized Revenue = €25,996,260.41; is_canceled = 1 Lost Revenue = €16,727,237.12!
💡 Why do we do this?

Reason: Three constructions convert a PMS export into analyzable shape. ArrivalDate: hotels store arrival as THREE columns (year, month name, day) — useless for any time chart until combined into one real date. TotalNights: stays are split weekend/week for accounting reasons, but revenue math needs one number. RoomRevenue: nights × ADR builds the money column everything else depends on. And the SUMIFS verification establishes the set's core lesson BEFORE any dashboard exists: booked revenue (€42.72M) ≠ earned revenue (€26.00M), because 37% of bookings never check in.

Real-time example: This distinction is worth €16.73M in this dataset — the amount of "revenue" that exists only as cancelled reservations. A revenue manager who reports €42.72M has inflated their year by 64% and will budget staffing, purchasing, and cash flow against rooms that were never occupied. That's Mistake 1, and it's the hospitality version of the semi-additive trap: booked value is a promise, realized value is a fact — reports must separate them (and the leakage IS valuable: it's the size of the prize for better deposit policies).

What happens if you skip it: No working ArrivalDate means no seasonality chart; no split of realized vs cancelled means the single most important number in revenue management is wrong.

Smart-work tip: Whenever an event has a lifecycle (booked → checked-in / cancelled / no-show), compute the value at EACH lifecycle stage, not just the total. The gaps between stages are where every operational decision lives.

5. Phase B — Complete Power BI & Small Multiples Journey

Stage 1 & 2 — Clean PMS Strings, Build ArrivalDate & Lead-Time Bands in Power Query

  1. Import data/hotels.csv → Transform Data → rename query to Bookings.
  2. Fix "NA" & "NULL": On column children, Replace Values NA → 0, then set type = Whole Number. On country, replace NULL → Unknown.
  3. Build ArrivalDate: Click Add Column → Custom Column → Name: ArrivalDate → Formula: 
    Date.FromText([arrival_date_month] & " " & Text.From([arrival_date_day_of_month]) & ", " & Text.From([arrival_date_year]), "en-US")
    Set ArrivalDate Data Type = Date!
  4. Add TotalNights: Custom Column = [stays_in_weekend_nights] + [stays_in_week_nights] (Whole Number).
  5. Add Ordered LeadTimeBand & LeadTimeSort: 
    // LeadTimeBand:
if [lead_time] <= 7 then "0–7d (Last Min)"
else if [lead_time] <= 30 then "8–30d"
else if [lead_time] <= 90 then "31–90d"
else if [lead_time] <= 180 then "91–180d"
else "181d+ (6m+)"
    (Add matching LeadTimeSort 1..5!). Click Home → Close & Apply.
💡 Why do we do this?

Reason: Two PMS quirks get neutralized here. (1) Literal text codes: children stores the STRING "NA" in 4 rows — leave it and the Whole-Number conversion throws errors (Mistake 2); country stores the literal string "NULL" which is NOT a null — a value-based distinction you can only catch by reading the data, not the type. (2) The Date.FromText(..., "en-US") pattern rebuilds a real date from month-NAME + day + year, with the locale pinned so "July 1, 2016" parses identically on every machine. The LeadTimeBand column then converts the raw lead_time integer (0–629 days!) into 5 ordered risk bands — the ladder the cancellation analysis climbs.

Real-time example: Why bands instead of raw days: charting cancellation rate against 629 individual lead-time values produces a noisy scatter-ish line where the staircase (9.6% → 57%) is invisible. Five bands make the pattern chartable AND actionable — revenue managers set policies per band ("deposits required for 181d+"), not per day. The LeadTimeSort companion column is the familiar Sort-by-column pattern ensuring the bands run young→old, never alphabetically.

What happens if you skip it: Four conversion errors block the load, "NULL" shows up as a fake country on the map, dates parse differently per laptop, and lead-time risk analysis drowns in 629 ungrouped days.

Smart-work tip: Always pin locale explicitly when parsing text dates built from parts — implicit parsing is machine-dependent and will break on a colleague's laptop with different regional settings. And bucket any wide-range risk variable (days, age, credit score) into ordered bands before analyzing — bands are what policies are written against.

Stage 3 & 4 — Calendar Table & Hospitality DAX Measures

Create a Calendar table (2015-07-01 to 2017-08-31), relate Calendar[Date] → Bookings[ArrivalDate], and sort Bookings[LeadTimeBand] by LeadTimeSort. Then write:

Total Bookings = COUNTROWS ( 'Bookings' )
// Check: 119,390

Cancelled Bookings =
CALCULATE ( [Total Bookings], 'Bookings'[is_canceled] = 1 )
// Check: 44,224

Cancellation Rate % = DIVIDE ( [Cancelled Bookings], [Total Bookings] )
// Check: 37.04% (City = 41.73%, Resort = 27.76%)

Booked Room Revenue =
SUMX ( 'Bookings', 'Bookings'[TotalNights] * 'Bookings'[adr] )
// Check: €42,723,497.53

Realized Revenue =
CALCULATE ( [Booked Room Revenue], 'Bookings'[is_canceled] = 0 )
// Check: €25,996,260.41

Cancelled Revenue Leakage =
CALCULATE ( [Booked Room Revenue], 'Bookings'[is_canceled] = 1 )
// Check: €16,727,237.12

Avg ADR = AVERAGE ( 'Bookings'[adr] )
// Check: €101.83
💡 Why do we do this?

Reason: The measure family here implements the lifecycle revenue split from Step A1 as reusable DAX: Booked Room Revenue (all promises, €42.72M), Realized Revenue (kept promises, €26.00M), and Cancelled Revenue Leakage (broken promises, €16.73M). All three come from ONE SUMX core with different is_canceled filters — one definition, three lenses, no disagreement possible. Cancellation Rate % then becomes a ratio that must be sliced to be understood: 37.04% overall hides that City hotels leak at 41.73% while Resorts leak at 27.76%.

Real-time example: Why the split matters operationally: leakage of €16.73M is not "lost forever" — it's recoverable through policy. Deposit requirements on long-lead bookings, stricter group contracts, and smarter overbooking all target specific leakage slices, and each measure above feeds one chart that locates the slice (Visual 3 finds WHEN guests cancel, Visual 4 finds WHO cancels). A revenue manager with this measure set can quantify any policy change ("if long-lead cancellations drop by a third, that's €X back") before negotiating it with the GM.

What happens if you skip it: Reports quote booked revenue (Mistake 1: +64% inflation), cancellation analysis stays at the blended 37%, and every overbooking/deposit decision is made on vibes.

Smart-work tip: Define revenue measures at each lifecycle stage ONCE, then let every chart combine them. And never report a blended rate (37%) without its segment split — averages across properties hide the exact variance the business needs to act on (city ≠ resort here, dramatically).

Visual 2 City vs. Resort Seasonality — Small Multiples Line Chart (First Time in This Course!)

Why Small Multiples? Instead of tangling multiple lines together, Power BI's Small multiples well splits one chart into a synchronized side-by-side trellis sharing the exact same Y-axis!

X-axisCalendar[MonthShort] (Jan–Dec)
Y-axis[Realized Revenue] (or [Avg ADR])
Small multiplesBookings[hotel] (1 row × 2 columns grid in Format pane!)

Instant Insight: Algarve Resort Hotel ADR & revenue skyrocket in July–August beach vacation months, while Lisbon City Hotel stays steady Spring through Autumn!

💡 Why do we do this?

Reason: The two hotels share a parent company but live in OPPOSITE seasonal worlds — which is exactly the situation Small Multiples were built for (the Set 03/09 pattern, now for side-by-side business comparison): synchronized Jan–Dec mini-charts sharing one Y-axis, so the eye compares shapes rather than decoding overlapping lines. One visual answers "how do our two properties differ seasonally?" without a single legend.

Real-time example: Read the trellis as the Revenue Director: the Resort panel shows a dramatic July–August spike (beach season: both occupancy AND rate climb — ADR surges), while the City panel stays broad and steady spring-through-autumn (business + city-break travel). The management consequence is real money: pricing strategy, staffing, and maintenance windows must be scheduled OPPOSITELY per property — the Resort discounts hard in winter and maxes rates in August; the City hotel can hold rates year-round. Merging both into one averaged line would erase this contrast and misprice BOTH properties.

What happens if you skip it: An averaged "hotel group" seasonal curve shows a mild summer bump that describes NEITHER property — the Resort's 3× summer peak and the City's steady baseline both wash out, and pricing decisions get made against fiction.

Smart-work tip: When comparing 2–8 groups over time where the SHAPE is the message, small multiples beat multi-line charts — separate panels, shared scales. Put volume in the Y-axis and price (ADR) in a second chart or tooltip; never average a rate across properties without showing each.

Visual 3 & 4 Lead-Time Cancellation Combo + Channel Leakage Stacked Bar

1. Line and clustered column chart: X-axis = Bookings[LeadTimeBand], Column Y-axis = [Total Bookings], Line Y-axis = [Cancellation Rate %]. Recommend requiring deposits or controlled overbooking for 181d+ reservations (57.0% cancellation rate)!
2. Stacked bar chart: Y-axis = Bookings[market_segment], X-axis = [Realized Revenue] and [Cancelled Revenue Leakage].

💡 Why do we do this?

Reason: These two charts turn the leakage number into a POLICY. The lead-time combo shows cancellation risk rising monotonically from 9.63% (last-minute bookings — people who show up because they're already traveling) to 57.01% (6-month-out bookings — plans that changed). The channel stacked bar then shows WHERE the leakage concentrates: Groups cancel at 61.06% while Direct bookings cancel at just 15.34% — same rooms, wildly different reliability. Together they answer the brief's overbooking question with a segmentation, not a guess.

Real-time example: Walk through the revenue-management decisions these charts license: (1) require deposits on 181d+ bookings — the band where over half the inventory promised never shows; (2) negotiate group contracts with attrition clauses (groups book early AND cancel at 61% — the worst of both); (3) invest in the Direct channel — the 15.34% cancel rate makes every direct euro worth ~4 direct-euros of reliability versus Groups. Each recommendation cites a measured band or segment; the GM approves policies, not hunches. The column layer (booking volume per band) matters too: it shows the 181d+ band isn't a tiny edge case — 24,692 bookings live there.

What happens if you skip it: Overbooking is calibrated on the blended 37% — meaning the hotel double-sells too aggressively on last-minute bookings (9.6% risk) and not aggressively enough on long-lead ones (57%) — losing both occupancy AND credibility at once.

Smart-work tip: A risk variable plus a rate line plus a volume column is the universal "calibration" chart (works for loan default by age band, churn by tenure, no-show by lead time). Volume columns keep the tail bands honest — policy only matters where the bookings actually are.
