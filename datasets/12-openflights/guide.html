\n The \\N Sentinel & 2-Table Star Schema:
\n 1. MySQL Export \\N: Empty fields in the OpenFlights export are written as literal \\N text (not blank!). If left alone, Power BI treats them as text, blocking numeric relationships on airport_id and corrupting coordinates.
\n 2. Two Tables, One Relationship: Airports (7,698 entities) is the dimension; Routes (67,663 events) is the fact. The join key is airport_id (1..7,698), NEVER the iata code (1,626 missing codes!).
\n 3. International vs Domestic: Same country on both ends = Domestic (48.02%); different countries = International (51.98%); unmatched = 892 routes.

4. Phase A — Step-by-Step in Microsoft Excel (XLOOKUP Across 2 Sheets)

Step A1 — Load Routes & Airports into Two Tabs

In Excel, use Data → From Text/CSV (UTF-8) to load airports.csv onto sheet Airports and routes.csv onto sheet Routes.
💡 Why do we do this?

Reason: For the first time in the course, you're not cleaning one table — you're preparing a relationship between two tables: Routes (the fact: 67,663 events) and Airports (the dimension: 7,698 entities). Everything downstream — VLOOKUP, XLOOKUP, star schema, relationships — depends on loading them cleanly and separately, each into its own named tab, from UTF-8 (airport names like São Paulo again).

Real-time example: This two-tab structure is the miniature version of every real BI warehouse: one long \"events\" table (flights, orders, clicks) and one \"directory\" table (airports, customers, products) that describes the entities the events point at. The reason airports live separately is obvious the moment you think about updates: airport data (coordinates, names) changes rarely; route data changes constantly. Separating them means 7,698 rows of description stored once instead of duplicated across 67,663 route rows — smaller file, single point of truth, no contradictions.

What happens if you skip it: Merging or mangling the two loads at import time forces manual column-copying later, and any airport attribute fix has to be applied 67,663 times instead of once.

Smart-work tip: Name tabs after tables and keep fact/dimension roles clear from the first minute — the mental model (long events + short directory + a key connecting them) is the same one you'll use in every database and BI tool for the rest of your career.

// In the Fields pane, drag RouteScope into Rows, and drag source_airport_id (set to Count) and dest_airport_id (set to Count) into Values.
// Format the counts (34,710 / 32,061 / 892) and confirm the percentages (51.98% / 48.02%) match the Excel audit!
💡 Why do we do this?

Reason: Three decisions in one step. (1) Join on airport_id, never iata: 1,626 small airfields have \\N instead of an IATA code, so an iata-join produces duplicate-key collisions and lost rows — while airport_id is a unique 1..7,698 surrogate key with zero blanks. (2) Graceful misses: XLOOKUP and Matrix's Count both handle unmatched values cleanly, labeling them as "Unmatched" in Excel and counting them in Power BI Matrix (892 rows) instead of crashing — and the RouteScope formula routes them to an honest "Unmatched" bucket instead of silently calling them Domestic. (3) Derived classification: RouteScope (same country on both ends = Domestic) turns two lookups into the business answer the client asked for. Both engines independently compute the target numbers to prove the data integrity.

Real-time example: Feel what the wrong key does: join on iata and every \"\\N\" source/destination route either fails to match or worse, collides — rows vanish or multiply, and the \"Total Routes = 67,663\" card starts drifting by hundreds with no error message. The VALUE(D2) wrapper matters too: routes.csv stores IDs as text, and a text \"1852\" will never match the numeric 1852 — Excel's classic VLOOKUP #N/A that isn't really about missing data at all. The PivotTable and Matrix independently verify the 51.98% / 48.02% split.

What happens if you skip it: Mistake 1 in full: mangled many-to-many joins, phantom mismatches, and an international/domestic split computed over the wrong subset of routes.

Smart-work tip: When a dimension offers both a business code (IATA) and a surrogate integer key, join on the surrogate — business codes get reused, blanked, and recycled; surrogate keys don't. And always give lookups a fallback value: an explicit \"Unmatched\" bucket is data you can audit; #N/A is data that stops your whole column. PivotTable and Matrix are the cheap insurance that stops nonsense from ever reaching a chart.

5. Phase B — Complete Power BI 2-Table Modeling & Charts Journey

Stage 1 & 2 — Clean Airports & Routes in Power Query

  1. Import data/airports.csv (UTF-8) → Transform Data → rename query to Airports. Select all columns (Ctrl + A) → Replace Values → Find: \\N → Replace with: null. Set airport_id = Whole Number, and latitude, longitude, altitude = Decimal Number. Add Custom Column HubLabel: if [iata] = null then [name] else [iata] & \" — \" & [city].
  2. Click New Source → Text/CSV → select data/routes.csv → rename query to Routes. Select all columns → Replace Values \\N → null. Set source_airport_id, dest_airport_id, and stops = Whole Number.
  3. In Routes, replace blank \"\" in codeshare with \"Operated\" and \"Y\" with \"Codeshare\" so legends read clearly!
  4. Click Home → Close & Apply.
💡 Why do we do this?

Reason: Every MySQL-flavored export uses the string \\N to mark nulls, and here it poisons the JOIN KEYS specifically: source_airport_id and dest_airport_id must become Whole Numbers to match Airports[airport_id] — the literal text \"\\N\" blocks that conversion for every row it touches. Replacing across ALL columns of BOTH tables in one pass (Ctrl+A → Replace Values) also catches hidden sentinels in columns you weren't watching (e.g., altitude). The HubLabel and codeshare renames are presentation hygiene: \"Y\"/\"\" legends force users to memorize a codebook.

Real-time example: Watch the failure if you skip the replace: Power BI tries to type source_airport_id as Whole Number, hits \"\\N\" rows, and throws an error on load — or worse, leaves the column as Text, so the relationship to Airports silently matches nothing (dashed join, zero-filtered visuals). And the readability win is real: \"Y\" vs blank as a legend makes every airline chart unreadable; \"Codeshare\" vs \"Operated\" reads itself.

What happens if you skip it: Relationships form on the wrong type, maps get phantom pins at null coordinates, and slicer items show literal \"\\N\" entries — the classic MySQL-export smell in a Power BI model.

Smart-work tip: On any database-flavored CSV, do a global \"\\N → null\" sweep FIRST, before typing columns — sentinels in key columns block type conversion, and sentinels in measure columns corrupt aggregates. Ten seconds here saves an hour of \"why won't this relationship form?\"

Stage 3 — Build 2-Table Star Schema Relationship

Open Model view: connect Airports[airport_id] (1) → (*) Routes[source_airport_id] and Airports[airport_id] (1) → (*) Routes[dest_airport_id]. Set Cross-filter direction = Both (so clicking an Airport slices the Route fact table, and clicking a Route filters the Airport dimension).
💡 Why do we do this?

Reason: This is the textbook star schema: one dimension table (Airports) feeds two foreign keys in the fact table (Routes). The relationship direction (Both) allows the map and matrix visuals to filter each other seamlessly. The surrogate key airport_id guarantees zero collisions (unlike IATA codes, where 1,626 rows have \\N).

Real-time example: Click a hub airport on the map (e.g., LHR London) and the Route Matrix instantly filters to only routes touching LHR. The 51.98% / 48.02% split recalculates for that hub. Without the relationship, the map and matrix are two disconnected pictures; with it, they're one interactive model.

What happens if you skip it: The dashboard becomes two separate reports. Clicking an airport does nothing to the routes, and the client's "International vs Domestic" question can't be sliced by hub.

Smart-work tip: Always verify relationship cardinality (1:*) and direction (Both/Single) after loading. A star schema is only as strong as its join keys — surrogate integers (airport_id) beat business codes (iata) every time.

Stage 4 — DAX Measures

Total Routes = COUNTROWS ( 'Routes' )
// Check: 67,663

International Routes =
CALCULATE ( [Total Routes], 'Routes'[RouteScope] = \"International\" )
// Check: 34,710 (51.98%)

Domestic Routes =
CALCULATE ( [Total Routes], 'Routes'[RouteScope] = \"Domestic\" )
// Check: 32,061 (48.02%)

Unmatched Routes =
CALCULATE ( [Total Routes], 'Routes'[RouteScope] = \"Unmatched\" )
// Check: 892

International Share % = DIVIDE ( [International Routes], [Total Routes] - [Unmatched Routes] )
// Format: 0.0% -> shows 51.98%
// Check: 51.98%

Domestic Share % = DIVIDE ( [Domestic Routes], [Total Routes] - [Unmatched Routes] )
// Format: 0.0% -> shows 48.02%
// Check: 48.02%
💡 Why do we do this?

Reason: The measures mirror the Excel PivotTable audit exactly. Total Routes = COUNTROWS counts every event row. The scope measures filter by the derived RouteScope column. The share percentages divide by the matched total (66,771) excluding the 892 unmatched routes — matching the Excel PivotTable logic. The Matrix Visual confirms these numbers instantly.

Real-time example: The aviation team sees 51.98% International routes — a majority — which drives fleet planning (long-haul vs short-haul aircraft). The 892 unmatched routes flag data-quality gaps (missing airport IDs) that need manual correction in the source system. Both Excel and Power BI independently confirm the split, proving the model integrity.

What happens if you skip it: The split percentages drift (e.g., counting unmatched routes in the denominator) and the client's 51.98% / 48.02% benchmark is missed. The relationship breaks on \\N sentinels, and the map shows phantom pins.

Smart-work tip: Always audit the join key (airport_id) for nulls/sentinels BEFORE building relationships. PivotTable and Matrix are the cheap insurance that stops nonsense from ever reaching a chart.
