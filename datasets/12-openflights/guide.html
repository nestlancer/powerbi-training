4. Phase A — Step-by-Step in Microsoft Excel (XLOOKUP Across 2 Sheets)

Step A1 — Load Routes & Airports into Two Tabs

In Excel, use Data → From Text/CSV (UTF-8) to load airports.csv onto sheet Airports and routes.csv onto sheet Routes.
💡 Why do we do this?

Reason: For the first time in the course, you're not cleaning one table — you're preparing a relationship between two tables: Routes (the fact: 67,663 events) and Airports (the dimension: 7,698 entities). Everything downstream — VLOOKUP, XLOOKUP, star schema, relationships — depends on loading them cleanly and separately, each into its own named tab, from UTF-8 (airport names like São Paulo again).

Real-time example: This two-tab structure is the miniature version of every real BI warehouse: one long "events" table (flights, orders, clicks) and one "directory" table (airports, customers, products) that describes the entities the events point at. The reason airports live separately is obvious the moment you think about updates: airport data (coordinates, names) changes rarely; route data changes constantly. Separating them means 7,698 rows of description stored once instead of duplicated across 67,663 route rows — smaller file, single point of truth, no contradictions.

What happens if you skip it: Merging or mangling the two loads at import time forces manual column-copying later, and any airport attribute fix has to be applied 67,663 times instead of once.

Smart-work tip: Name tabs after tables and keep fact/dimension roles clear from the first minute — the mental model (long events + short directory + a key connecting them) is the same one you'll use in every database and BI tool for the rest of your career.

Step A2 — Enrich Routes Using XLOOKUP on airport_id

In Routes, add helper columns J (SourceCountry) and K (DestCountry) + L (RouteScope): 
// J2 (SourceCountry — looks up source_airport_id D2 in Airports!A:A -> returns Country D:D):
=XLOOKUP(VALUE(D2), Airports!$A$2:$A$7699, Airports!$D$2:$D$7699, "Unmatched")

// K2 (DestCountry — looks up dest_airport_id F2):
=XLOOKUP(VALUE(F2), Airports!$A$2:$A$7699, Airports!$D$2:$D$7699, "Unmatched")

// L2 (RouteScope — International vs Domestic):
=IF(OR(J2="Unmatched",K2="Unmatched"), "Unmatched", IF(J2=K2, "Domestic", "International"))
Verify with a PivotTable on RouteScope: 34,710 International (51.98%) vs. 32,061 Domestic (48.02%) across the 66,771 doubly-matched routes! Save as 12-openflights-clean.xlsx.
💡 Why do we do this?

Reason: Three decisions in one step. (1) Join on airport_id, never iata: 1,626 small airfields have \N instead of an IATA code, so an iata-join produces duplicate-key collisions and lost rows — while airport_id is a unique 1..7,698 surrogate key with zero blanks. (2) Graceful misses: XLOOKUP's 4th argument returns "Unmatched" instead of an error, so unmatched routes are LABELLED, not crashed — and the RouteScope formula routes them to an honest "Unmatched" bucket instead of silently calling them Domestic. (3) Derived classification: RouteScope (same country on both ends = Domestic) turns two lookups into the business answer the client asked for.

Real-time example: Feel what the wrong key does: join on iata and every "\N" source/destination route either fails to match or worse, collides — rows vanish or multiply, and the "Total Routes = 67,663" card starts drifting by hundreds with no error message. The VALUE(D2) wrapper matters too: routes.csv stores IDs as text, and a text "1852" will never match the numeric 1852 — Excel's classic VLOOKUP #N/A that isn't really about missing data at all.

What happens if you skip it: Mistake 1 in full: mangled many-to-many joins, phantom mismatches, and an international/domestic split computed over the wrong subset of routes.

Smart-work tip: When a dimension offers both a business code (IATA) and a surrogate integer key, join on the surrogate — business codes get reused, blanked, and recycled; surrogate keys don't. And always give lookups a fallback value: an explicit "Unmatched" bucket is data you can audit; #N/A is data that stops your whole column.

5. Phase B — Complete Power BI 2-Table Modeling & Charts Journey

Stage 1 & 2 — Clean Airports & Routes in Power Query

  1. Import data/airports.csv (UTF-8) → Transform Data → rename query to Airports. Select all columns (Ctrl + A) → Replace Values → Find: \N → Replace with: null. Set airport_id = Whole Number, and latitude, longitude, altitude = Decimal Number. Add Custom Column HubLabel: if [iata] = null then [name] else [iata] & " — " & [city].
  2. Click New Source → Text/CSV → select data/routes.csv → rename query to Routes. Select all columns → Replace Values \N → null. Set source_airport_id, dest_airport_id, and stops = Whole Number.
  3. In Routes, replace blank "" in codeshare with "Operated" and "Y" with "Codeshare" so legends read clearly!
  4. Click Home → Close & Apply.
💡 Why do we do this?

Reason: Every MySQL-flavored export uses the string \N to mark nulls, and here it poisons the JOIN KEYS specifically: source_airport_id and dest_airport_id must become Whole Numbers to match Airports[airport_id] — the literal text "\N" blocks that conversion for every row it touches. Replacing across ALL columns of BOTH tables in one pass (Ctrl+A → Replace Values) also catches hidden sentinels in columns you weren't watching (e.g., altitude). The HubLabel and codeshare renames are presentation hygiene: "Y"/"" legends force users to memorize a codebook.

Real-time example: Watch the failure if you skip the replace: Power BI tries to type source_airport_id as Whole Number, hits "\N" rows, and throws an error on load — or worse, leaves the column as Text, so the relationship to Airports silently matches nothing (dashed join, zero-filtered visuals). And the readability win is real: "Y" vs blank as a legend makes every airline chart unreadable; "Codeshare" vs "Operated" reads itself.

What happens if you skip it: Relationships form on the wrong type, maps get phantom pins at null coordinates, and slicer items show literal "\N" entries — the classic MySQL-export smell in a Power BI model.

Smart-work tip: On any database-flavored CSV, do a global "\N → null" sweep FIRST, before typing columns — sentinels in key columns block type conversion, and sentinels in measure columns corrupt aggregates. Ten seconds here saves an hour of "why won't this relationship form?"

Stage 3 — Build Active + Inactive Relationships in Model View (Interview Gold!)

Click Model view on the left rail:
1. Drag Airports[airport_id] onto Routes[source_airport_id] → verify One to many (1:*), Active = Checked (solid line!).
2. Now drag Airports[airport_id] onto Routes[dest_airport_id]! Because Power BI only allows ONE active path between two tables at a time, Power BI automatically creates this second line as an Inactive relationship (dashed line!) — which is exactly what we want!
3. Set Data Categories on Airports: latitude = Latitude, longitude = Longitude, country = Country. 
             Active (Solid Line: Origin)
Airports[airport_id] (1) ─────────────────► (*) Routes[source_airport_id]
Airports[airport_id] (1) - - - - - - - - -► (*) Routes[dest_airport_id]
             Inactive (Dashed Line: Destination — activated via USERELATIONSHIP!)
💡 Why do we do this?

Reason: Airports is a role-playing dimension — the same table describes an airport as an ORIGIN (source_airport_id) and as a DESTINATION (dest_airport_id). Power BI allows only one ACTIVE filter path between two tables (two active relationships would create contradictory, ambiguous filtering), so the second relationship is created inactive (dashed): dormant, but ready to be switched on by USERELATIONSHIP() whenever a measure needs the "destination" role. The alternative — duplicating Airports into OriginAirports + DestAirports — works, but then one airport slicer can't drive both sides, and the model doubles in size (Mistake 2).

Real-time example: The same pattern runs real analytics stacks everywhere: a Date table plays "Order Date", "Ship Date", and "Payment Date" roles; an Employee table plays "Manager" and "Report"; a Customer table plays "Buyer" and "Recipient". Modelers keep ONE copy of the dimension and multiple relationships, activating the needed role per measure. Learning it here on Airports (where the two roles have an intuitive meaning) is the standard interview-grade modeling lesson this stage promises.

What happens if you skip it: Only outbound analysis is possible; "how many routes land here?" (the inbound half of the brief) has no path through the model — or gets hacked with duplicated tables that break single-slicer interactivity.

Smart-work tip: Read the diagram convention: solid line = filter flows now, dashed = filter flows when summoned by USERELATIONSHIP. Draw this picture before writing the measures — knowing WHICH relationship serves which question is the whole design.

Stage 4 — Role-Playing DAX Measures

Outbound Routes = COUNTROWS ( 'Routes' )
// Overall: 67,663 | When sliced by Airports[iata]="ATL": 915!

Inbound Routes =
CALCULATE (
    COUNTROWS ( 'Routes' ),
    USERELATIONSHIP ( 'Airports'[airport_id], 'Routes'[dest_airport_id] )
)
// When sliced by Airports[iata]="ATL": 911! | "LAX": 498!

Net Route Imbalance = [Outbound Routes] - [Inbound Routes]

Codeshare Share % =
DIVIDE (
    CALCULATE ( [Outbound Routes], 'Routes'[codeshare] = "Codeshare" ),
    [Outbound Routes]
)
// Check overall: 21.57% (14,597 of 67,663)

Non-Stop Share % =
DIVIDE (
    CALCULATE ( [Outbound Routes], 'Routes'[stops] = 0 ),
    [Outbound Routes]
)
// Check overall: 99.98% (67,652 of 67,663)

Connected Hubs = DISTINCTCOUNT ( 'Routes'[source_airport_id] )
💡 Why do we do this?

Reason: [Outbound Routes] = COUNTROWS('Routes') works because the ACTIVE relationship filters Routes to rows departing the sliced airport — a plain count becomes origin-specific with zero extra syntax. [Inbound Routes] then does the magic: CALCULATE(COUNTROWS('Routes'), USERELATIONSHIP(Airports[airport_id], Routes[dest_airport_id])) temporarily swaps the active path for the inactive one, so the same airport row filters Routes by ARRIVAL instead. One dimension table, two filtering roles, two measures.

Real-time example: Verify it live as the guide says: slice to ATL — Outbound 915, Inbound 911 (nearly symmetric: Atlanta's Delta hub lands about as many as it launches). Slice to LAX — Outbound 492, Inbound 498 (slightly net-inbound: LA attracts more arrivals). Those tiny asymmetries, previously unmeasurable, are exactly what [Net Route Imbalance] exposes — and network planners care because imbalanced airports need repositioned aircraft and crews. Without USERELATIONSHIP, the inbound column simply cannot exist.

What happens if you skip it: You'd show every hub as "outbound only", the symmetry table collapses to one number, and half the client brief goes unanswered. Also note Non-Stop Share % = 99.98% — an almost-suspicious number worth flagging in commentary (this dataset records route legs, not journeys) — showing numbers, then questioning them, is analyst maturity.

Smart-work tip: Test inactive relationships with TWO contrasting airports (one symmetric, one asymmetric) — if both measures respond correctly, the role-switching works everywhere. And remember: USERELATIONSHIP only functions inside CALCULATE, never on its own.

💡 Why do we do this?

Reason: Airport coordinates are EXACT (down to runway precision), so a GPS lat/lon bubble map beats a country choropleth here — connectivity is a point-level phenomenon, not a national average. The >= 20 routes filter is a readability decision: 7,698 airports include thousands of tiny airstrips, and plotting them all turns the map into static; keeping the 300+ real hubs makes Atlanta, Heathrow, and Beijing glow as the network's arteries.

Real-time example: Read the map the way the alliance-planning team does: giant clusters over the US East (ATL, ORD, DFW), Western Europe (LHR, CDG, FRA), and East Asia (PEK) — the three legs of global connectivity, instantly visible as geography rather than a ranked table. Bubble size (outbound routes) shows relative dominance at a glance, while tooltips carry the negotiation detail: inbound routes and codeshare share for each hub. This is the "where should our alliance deepen partnerships?" view — the answer is literally pinned to the ground.

What happens if you skip it: Without the threshold filter, thousands of sub-20-route airfields drown the mega-hubs (the map becomes gray noise); without exact lat/lon, "Atlanta" might geocode to Atlanta, Texas or a national centroid — the Set 04 geocoding lesson, now with GPS precision available.

Smart-work tip: Match visual granularity to decision granularity: alliance strategy needs hubs (points), country-level policy needs choropleths (shapes). Use thresholds to control density — "show only what matters" is a legitimate, documented filter, not cheating.

Visual 3 Hub Symmetry Check — Clustered Bar Chart Powered by USERELATIONSHIP

Y-axisAirports[HubLabel] (Top 12 by [Outbound Routes])
X-axis[Outbound Routes] AND [Inbound Routes]

Verify Your Model Live: Hover over ATL — Atlanta: Outbound = 915, Inbound = 911! Hover over LAX — Los Angeles: Outbound = 492, Inbound = 498! That proves both your active and inactive relationships are working simultaneously!

💡 Why do we do this?

Reason: This chart is both an insight and a test. As insight: pairing Outbound and Inbound bars per hub reveals network symmetry — balanced hubs (ATL 915/911) are classic two-way connection machines, while asymmetric ones (LAX more inbound, some airports heavily net-outbound) reveal directional business roles like leisure destinations vs. departure megabases. As test: both bars appearing correctly per airport proves the active AND the USERELATIONSHIP-activated relationships work simultaneously in one visual — the model's hardest trick, verified in two hovers.

Real-time example: Why planners pay for this: a hub that launches 600 routes but receives 400 (net +200 outbound) is a fleet-origin imbalance — aircraft and crews pile up elsewhere and must be repositioned overnight (real cost). A near-zero imbalance hub like Atlanta is operationally self-balancing. The bar pair turns "symmetry" from a consultant's word into a visible, comparable measurement per airport — with the table (Visual 5) supplying the exact imbalance column for the top of the priority list.

What happens if you skip it: If the Inbound bar shows the SAME number as Outbound everywhere, the inactive relationship isn't being used (a classic copy-paste bug — both measures counting the active path), and the whole role-playing model is silently wasted.

Smart-work tip: When a measure uses USERELATIONSHIP, verify it against a visual where the two values must differ for at least one category — identical values everywhere is the smell of an inactive relationship that never activated.

For the client (an alliance-planning team), this chart quantifies WHO already behaves like an alliance partner and who never will — a targeting list for partnership outreach, derived from data alone.

What happens if you skip it: "Codeshare Share % = 21.6%" as one number hides the distribution entirely — the 21.6% is NOT spread evenly; it concentrates in legacy carriers while LCCs sit at ~0%, and that unevenness IS the insight.

Smart-work tip: Averages and totals describe populations; STACKS reveal composition — always split strategic metrics by the categorical that carries business meaning (business model, region, channel). And keep one numeric table per page as the "receipts" layer for whatever the charts dramatize.

8. Trainer's Troubleshooting: Common Beginner Mistakes

Mistake 1 — Joining on iata instead of airport_id: airports[iata] has 1,626 \N blanks, causing Many-to-Many join headaches! Always join on integer surrogate keys (airport_id) when available.
Mistake 2 — Duplicating the Airports table instead of using USERELATIONSHIP: Beginners often copy Airports into OriginAirports and DestAirports, but then a single Airport Slicer can't show both Outbound and Inbound together! USERELATIONSHIP solves that cleanly on one table.
