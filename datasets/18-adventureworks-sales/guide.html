💡 Why do we do this?

Reason: Enterprise finance has one iron rule: the numbers must reconcile to the source. Before building any model, you prove the pipeline's integrity by hand — summing Sales Amount and Total Product Cost in the raw sheet and computing Gross Profit yourself. This also fixes the DEFINITIONS in your head (Gross Profit = Sales − Cost; Margin = Profit ÷ Sales) that you'll re-encode as DAX measures minutes later. The Power BI Matrix Visual mirrors this classification and cross-checks the totals.

Real-time example: The CFO's brief makes a specific claim: revenue doubled from FY2018 ($23.86M) to FY2020 ($51.88M) while margin stayed at just 11.43%. Your hand arithmetic — $109,809,274.20 − $97,257,907.95 = $12,551,366.25, and 12.551 ÷ 109.809 = 11.43% — establishes the ground truth those claims rest on. Later, when your Power BI card shows exactly $109,809,274.20, the model is PROVEN; if it showed $109.7M, you'd know instantly something broke (wrong filter, wrong type). That reconciliation instinct is what separates a data analyst from a chart maker — and it's a PL-300 exam favorite. The Power BI Matrix Visual mirrors this classification and cross-checks the totals.

What happens if you skip it: A model error surfaces in the board meeting instead of in development — and once one number is challenged, EVERY number in the deck is doubted.

Smart-work tip: Keep a tiny \"source-of-truth\" scratch sheet of 5–6 verified totals per project. Any BI model is accepted or rejected by how it reconciles, not how it looks — make proving it a one-minute job. The Power BI Matrix Visual mirrors the classification and cross-checks the totals.

5. Phase B — Complete Power BI 7-Table Star Schema & Fiscal DAX

Stage 1 & 2 — Load & Polish the 7 Warehouse Tables

  1. Click Home → Excel workbook → select data/AdventureWorks-Sales.xlsx → check all 7 sheets → Transform Data.
  2. Rename each query to remove _data: Sales, Date, Product, Customer, Reseller, Territory, and Sales Order.
  3. Verify Date[Date] is Data Type = Date, all *Key columns are Whole Number, and Sales Amount / Total Product Cost are Fixed decimal number ($). Click Home → Close & Apply.
💡 Why do we do this?

Reason: A 7-table warehouse arrives dressed for programmers, not executives: sheet names like Sales_data, cryptic surrogate keys, and money columns that default to floating-point. Renaming to business words, typing money as Fixed decimal, and keeping keys as Whole Number is the hygiene pass that decides whether the model reads like a professional data product or a CSV dump. The Power BI Matrix Visual mirrors the classification and cross-checks the totals.

Real-time example: The Fixed-decimal choice is the one that bites hardest: 121,253 rows of Sales Amount must reconcile to the cent (your Step A1 total). Floating-point arithmetic introduces tiny drift — sums that show 109,809,274.20000001-style noise and occasionally miss reconciliation by a cent, exactly the kind of defect that erases trust in a finance review. Fixed decimal (the currency type) stores exact decimal values. Meanwhile, the renames pay off in every meeting: \"Sales, Product, Reseller, Territory\" need no translation for the CFO. The Power BI Matrix Visual independently confirms the totals and the fiscal year breakdown.

What happens if you skip it: Meetings argue about what Sales_data contains, money totals drift at the 10th decimal place, and joins on mistyped keys silently drop rows.

Smart-work tip: Rename in Power Query (not just Model view) so names propagate everywhere, and adopt the type discipline: Whole Number = keys, Fixed Decimal = money, Date = dates. It's the same typing law every set in this course has enforced — now at warehouse scale. The Power BI Matrix Visual mirrors the classification and cross-checks the totals.

Stage 3 — Wire the 7-Table Star Schema + Mark Date Table

1. In Model view, verify (or drag) 1-to-Many single-direction relationships from Product[ProductKey], Customer[CustomerKey], Reseller[ResellerKey], Territory[SalesTerritoryKey], and Sales Order[SalesOrderLineKey] (ensure Sales Order filters Sales!) into Sales.
2. Drag Date[DateKey] → Sales[OrderDateKey] (Active), then drag Date[DateKey] → Sales[ShipDateKey] (Inactive) and Sales[DueDateKey] (Inactive).
3. Right-click Date → Mark as date table → choose column Date[Date]! And select Date[Month] → Sort by column → MonthKey!
4. Create a formal Hierarchy on Product: right-click Category → Create hierarchy → add Subcategory, Model, and Product!
💡 Why do we do this?

Reason: This stage builds the Kimball star: six dimensions radiating from one fact table, filters flowing one way (dimension → fact). The special problem here is TIME: every fact row carries THREE dates (ordered, shipped, due), but a schema allows only ONE active relationship per pair of tables — so Date must role-play: active via OrderDateKey, and two inactive relationships (ShipDateKey, DueDateKey) that measures can activate on demand. Marking the table as a date table then unlocks all time-intelligence functions, and sorting Month by MonthKey stops alphabetical month chaos. The Power BI Matrix Visual mirrors the classification and cross-checks the totals.

Real-time example: The CFO's ask \"compare revenue when the order was PLACED vs when it left the warehouse\" is ONLY possible because of the inactive ship-date relationship — one USERELATIONSHIP measure (Set 12's trick, now on dates) switches the filter path from order-date to ship-date, and Visual 3's backlog gap becomes measurable. The fiscal calendar matters just as much: AdventureWorks' year ends June 30, so FY2020 runs July 2019–June 2020; without \"Mark as date table\" the YTD functions misbehave, and without the fiscal awareness Stage 4's \"6/30\" argument the year would wrongly start in January. The Power BI Matrix Visual independently confirms the $109,809,274.20 Sales, $97,257,907.95 Cost, and $12,551,366.25 Gross Profit (11.43%) totals.

What happens if you skip it: Ordered-vs-shipped analysis becomes impossible (one date path only), TOTALYTD/SAMEPERIODLASTYEAR error out or return wrong periods, and month slicers read April, August, December... alphabetically.

Smart-work tip: Hide ALL *Key columns in Report view — a star schema with hidden keys is the industry-standard shape and a guaranteed PL-300 question. And the first calendar question to ask ANY finance client: \"when does your fiscal year end?\" More BI deployments fail on calendar mismatch than on complex DAX. The Power BI Matrix Visual mirrors the classification and cross-checks the totals.

Stage 4 — Enterprise Financial & Fiscal Time Intelligence DAX

Write the core measures on the 7-table star schema:

Total Sales = SUM ( 'Sales'[Sales Amount] )
// Check: $109,809,274.20

Total Product Cost = SUM ( 'Sales'[Total Product Cost] )
// Check: $97,257,907.95

Gross Profit = [Total Sales] - [Total Product Cost]
// Check: $12,551,366.25

Gross Margin % = DIVIDE ( [Gross Profit], [Total Sales] )
// Format: 0.00%
// Check: 11.43%

Fiscal Year Total Sales =
CALCULATE ( [Total Sales], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
// Check: FY2018 ($23.86M) · FY2019 ($34.07M) · FY2020 ($51.88M)

Order vs Ship Gap =
VAR Ordered = [Total Sales]
VAR Shipped = CALCULATE ( [Total Sales], USERELATIONSHIP ( 'Date'[DateKey], 'Sales'[ShipDateKey] ) )
RETURN Ordered - Shipped
// Check: Backlog gap visible in Visual 3
💡 Why do we do this?

Reason: The measures implement the enterprise finance reconciliation: Total Sales, Total Product Cost, and Gross Profit (11.43%) match the Excel PivotTable and Power BI Matrix audit ($109,809,274.20 / $97,257,907.95 / $12,551,366.25). The fiscal time intelligence handles the June 30 year-end, and the role-play date relationships allow comparing ordered vs shipped revenue. The Power BI Matrix Visual independently confirms the totals and the fiscal year breakdown.

Real-time example: The CFO sees the $109.81M Sales and $97.26M Cost reconcile exactly to the $12.55M Gross Profit (11.43% margin) verified in the PivotTable and Matrix. The fiscal year comparison (FY2018 $23.86M → FY2020 $51.88M) shows doubling revenue, while the ship-date vs order-date gap reveals backlog. The PivotTable and Matrix audit is the insurance that stops nonsense from ever reaching a chart.

What happens if you skip it: The model drifts from the $109.81M / $97.26M / $12.55M reconciliation, fiscal year calculations error out, and the role-play date relationships break. The PivotTable and Matrix cross-check is the cheap insurance that stops nonsense from ever reaching a chart.

Smart-work tip: Always reconcile source totals in Excel PivotTable and Power BI Matrix before building DAX. Hide *Key columns, mark the date table, and sort months by key. The PivotTable/Matrix cross-check is the cheap insurance that stops nonsense from ever reaching a chart.
