4. Phase A — Step-by-Step in Microsoft Excel (day.csv, 731 Rows)

Step A1 — Open day.csv & Verify Data Integrity

  1. Open Excel → Data → From Text/CSV → select datasets/05-bike-sharing/data/day.csv → Delimiter = Comma → Load.
  2. Format column B (dteday) as Date and columns N:P (casual, registered, cnt) as #,##0.
  3. Integrity Check Formula (Column Q): In Q1 type MathCheck, and in Q2 type =(N2+O2)-P2. Check the filter dropdown on MathCheck: the ONLY value is 0! Every single day balances to the exact trip.
💡 Why do we do this?

Reason: This is a reconciliation check — the data-analyst's version of an accountant's balance check. The codebook promises casual + registered = cnt on every row; proving it in one formula converts "I read the documentation" into "I verified the file". It also detects the worst kind of bug: partially broken data where most rows are fine but a few are corrupt.

Real-time example: Imagine one bad export where cnt was written before casual finished updating: a handful of rows would show MathCheck = -37 instead of 0. Without the check, your Registered Share % would be quietly wrong and nobody would ever know why it disagreed with the finance team's number. With the check, the filter dropdown IS the audit: one value, 0, across all 731 days — the file's internal math is sound and you can build on it with confidence.

What happens if you skip it: You discover additive inconsistencies months later, when two dashboards disagree — and nobody remembers which file, which column, or which export caused it.

Smart-work tip: Whenever a dataset defines relationships between columns (parts = total, subtotal = sum of lines), encode that promise as a formula column and check that it's always 0. It costs 30 seconds and certifies the file like a tamper seal.

Step A2 — Add Readable Labels in Excel (Columns R & S)

  1. Column R — SeasonName: =CHOOSE(C2, "1. Winter-Spring", "2. Spring-Summer", "3. Peak Summer", "4. Autumn")
    Beginner Bonus Function! Whenever a code is cleanly 1, 2, 3, 4, Excel's CHOOSE() is much shorter and cleaner than four nested IFs!
  2. Column S — TempCelsius: =ROUND(J2*47-8, 1) (converts normalized 0–1 temperature into readable °C using the UCI scaling C = temp × 47 − 8).
💡 Why do we do this?

Reason: Numeric codes are for databases, not for humans. A chart axis that says "Season 3 is best" forces every reader to guess — and stakeholders don't guess, they disengage. Translating codes into labeled categories ("3. Peak Summer") and normalized fractions into real units (temp 0.72 → 25.8°C) makes the data speak the client's language. And CHOOSE() exists precisely for clean 1-to-n codes: one short function replaces four nested IFs and is far harder to typo.

Real-time example: Two versions of the same slide: "Rides peak in Season 3" (audience squints, someone asks "is that fall?") versus "Rides peak in Peak Summer — 1,061,129 rides" (instant nodding). The temperature translation matters even more for operations: "avg temp 0.61" means nothing to a fleet manager, but "20.7°C" triggers the immediate insight — "that's when our docks empty out" — because humans reason in weather units, not normalization math.

What happens if you skip it: Sign-off checklist item #5 fails: charts displaying raw mystery codes like "Weathersit 1" get returned with the note "please translate", and you redo formatting on every visual.

Smart-work tip: Notice the number prefixes ("1. Winter-Spring"…) — the same alphabetization trick from earlier sets, keeping codes AND their labels sorted logically in every slicer. Translate codes once, at import; never leave translation work to whoever is presenting.

Step A3 — PivotTable Check

Insert a PivotTable: Rows = SeasonName, Columns = yr, Values = Sum of cnt. Confirm 3. Peak Summer = 1,061,129, yr 0 (2011) = 1,243,103, yr 1 (2012) = 2,049,576, and Grand Total = 3,292,679 across 731 daily rows! Save as 05-bike-sharing-day-check.xlsx.
💡 Why do we do this?

Reason: This pivot does double duty: it verifies totals (3,292,679 rides — the number that must re-appear in Power BI from the other file) and previews the cross-sectional story (season × year). The light 731-row file is ideal for this: pivots are instant, and Excel is the cheapest place to find and fix misunderstanding before the model is built.

Real-time example: Read the cross-tab and a business insight appears before any Power BI work: Peak Summer is the #1 season (1,061,129), but look at the year split — 2012 alone (2,049,576) is 65% bigger than 2011 (1,243,103), with growth in EVERY season. That's the growth narrative the Director of Fleet Operations will care about ("is the network booming, or just summer?") — and you now know the answer before designing a single visual. The pivot shaped the report's storyline.

What happens if you skip it: You'd discover in Power BI that "Season 3" needs translating, that 2012 dominates, and that your totals don't match the codebook — three findings you could have had in Excel in five minutes, now discovered mid-build.

Smart-work tip: Use the small-grain file as your scratchpad and the fine-grain file as your model. Quick questions → Excel pivot; dashboard questions → Power BI. Choosing the lightest tool for each question is exactly the "smart work" mindset this course teaches.

5. Phase B — Complete Power BI & Charts Journey (hour.csv, 17,379 Rows)

Stage 1 & 2 — Load hour.csv & Translate Codes in Power Query

  1. In Power BI Desktop, click Home → Text/CSV → select data/hour.csv (leave day.csv alone!) → click Transform Data. Rename query to Trips.
  2. Set dteday = Date; hr, weekday, casual, registered, cnt = 123 (Whole Number); temp, atemp, hum, windspeed = 1.2 (Decimal Number).
  3. Add 4 Human-Readable Conditional Columns (Add Column → Conditional Column):
    • DayType: If workingday = 1 → Working Day, Else → Weekend / Holiday.
    • WeatherLabel: 1 → 1. Clear · 2 → 2. Mist / Cloudy · 3 → 3. Light Rain / Snow · Else → 4. Heavy Storm.
    • SeasonLabel: 1 → 1. Winter-Spring · 2 → 2. Spring-Summer · 3 → 3. Peak Summer · Else → 4. Autumn.
    • WeekdayShort (Custom Column): List.Range({"Sun","Mon","Tue","Wed","Thu","Fri","Sat"}, [weekday], 1){0} (or Conditional Column 0=Sun … 6=Sat).
  4. Click Home → Close & Apply. Confirm 17,379 rows load into Trips!
💡 Why do we do this?

Reason: This step teaches grain discipline — the most important data-modeling concept in the entire practice set. day.csv and hour.csv contain the SAME 3,292,679 rides at two grains; loading both and relating them on dteday means one daily row matches 24 hourly rows, and Power BI starts multiplying numbers by 24. One fact per grain: you load the FINEST grain you need (hour — it answers daily, monthly, and annual questions too, because date and hour both live in it) and nothing coarser.

Real-time example: The dispatch questions demand hours ("which hour gets slammed?"), so hour.csv is mandatory. Now notice it also covers the annual question: summing cnt by yr gives 2011 = 1,243,103 and 2012 = 2,049,576 — identical to the day file, because both files describe the same rides. That's the power of the finest grain: it can always aggregate UP, but a coarse grain can never drill DOWN.

What happens if you skip it: Mistake 1 from the troubleshooting section: totals multiply by 24, cross-filtering breaks, and a debugging afternoon is spent finding why "Total Rides" shows 79 million.

Smart-work tip: Before loading ANY file ask: "what is one row here, and what's the smallest grain my questions need?" Load exactly that grain (17,379 rows, not 17,379 + 731). Hourly data answers hourly AND daily questions; daily data cannot answer hourly ones.

Stage 3 — Model View: Calendar Table & Weekday Sorting

  1. In Data view → New table, create a continuous 2011–2012 Calendar: 
    Calendar =
ADDCOLUMNS (
    CALENDAR ( DATE ( 2011, 1, 1 ), DATE ( 2012, 12, 31 ) ),
    "Year", YEAR ( [Date] ),
    "MonthNum", MONTH ( [Date] ),
    "Month", FORMAT ( [Date], "MMM" ),
    "YearMonth", FORMAT ( [Date], "YYYY-MM" )
)
    Mark as date table, sort Month by MonthNum, and relate Calendar[Date] (1) → Trips[dteday] (*).
  2. On Trips, select WeekdayShort → Column tools → Sort by column → weekday (so columns run Sun, Mon, Tue, Wed, Thu, Fri, Sat!). Also set hr Summarization = Don't summarize.
💡 Why do we do this?

Reason: Same two modeling laws as earlier sets, now on dispatch data. (1) A continuous Calendar table feeds time intelligence — without it, SAMEPERIODLASTYEAR in the YoY measure has no complete 2011–2012 timeline to walk. (2) Text sorts alphabetically unless you attach a numeric sort key — "Fri, Mon, Sat, Sun…" is useless for spotting commuter patterns; Sun → Sat puts days in riding order. And hr with "Don't summarize" stays an identity (a time slot), never "sum of hours = 276".

Real-time example: Picture the heatmap matrix (Visual 3) with unsorted weekday columns: Fri, Mon, Sat, Sun, Thu, Tue, Wed. The dispatcher's core pattern — quiet Sunday left edge, slammed Tuesday–Friday right edge — is scrambled into noise. After Sort by column = weekday, the left-to-right rhythm of the week becomes visible in one sweep of the eye, which is literally how the rebalancing schedule gets designed.

What happens if you skip it: YoY % returns blank or wrong values (no marked date table), the heatmap reads in alphabetical gibberish, and hour slicers show "sum = 276 hours".

Smart-work tip: Any ordered text column (weekday, month, time slot) gets a numeric companion column + Sort by column — make it reflex. And every fact table with dates gets a marked continuous Calendar; it's the entry ticket to time intelligence.

Stage 4 — DAX Measures (Beginner → Advanced)

Total Rides = SUM ( 'Trips'[cnt] )
// Format: #,0 -> Check: 3,292,679 (exact match to day.csv!)

Hourly Rows = COUNTROWS ( 'Trips' )
// Format: #,0 -> Check: 17,379

Registered Rides = SUM ( 'Trips'[registered] )
// Check: 2,672,662

Casual Rides = SUM ( 'Trips'[casual] )
// Check: 620,017

Registered Share % = DIVIDE ( [Registered Rides], [Total Rides], 0 )
// Format: 0.0% -> Check: 81.2% (81.17%)

Casual Share % = DIVIDE ( [Casual Rides], [Total Rides], 0 )
// Format: 0.0% -> Check: 18.8% (18.83%)

Avg Hourly Rides = AVERAGE ( 'Trips'[cnt] )
// Format: 0.0 -> Check: 189.5 rides/hr overall (525.3 at 5pm on Working Days!)

Avg Temp Celsius = AVERAGE ( 'Trips'[temp] ) * 47 - 8
// Format: 0.0°C

Rides YoY % =
VAR PriorYr = CALCULATE ( [Total Rides], SAMEPERIODLASTYEAR ( 'Calendar'[Date] ) )
RETURN
    IF ( NOT ISBLANK ( PriorYr ), DIVIDE ( [Total Rides] - PriorYr, PriorYr ) )
// Select Year = 2012 -> Check: +64.9% (+64.88%)
💡 Why do we do this?

Reason: These measures encode the right aggregation for each physical quantity — the habit that separates correct dashboards from quietly-wrong ones. Rides are counts → SUM. "How slammed is an hour?" is an intensity → AVERAGE(cnt) per hour. Temperature is a state reading → AVERAGE only (summing 24 hourly temps yields nonsense "14.2 normalized degrees"). And the YoY measure wraps DIVIDE in an ISBLANK guard so 2011 (no prior year) stays blank instead of showing an error.

Real-time example: Watch the same data produce two valid but different answers: Total Rides = 3,292,679 (annual capacity story) versus Avg Hourly Rides = 189.5 (dispatch intensity story). The Director asks "are we slammed?" — the honest answer is 525.3 rides at 5pm on working days, not "525,000 rides in September". Choosing the wrong one of these two measures produces a technically-correct number that answers nobody's question. Also note the exact reconciliation: 2,672,662 + 620,017 = 3,292,679 — your measures inherit the file's integrity from Step A1.

What happens if you skip it: Weather columns get summed into gibberish, intensity questions get answered with totals, and YoY shows -100% or infinite values for 2011 because the blank-guard is missing.

Smart-work tip: For every measure ask: count, sum, or average? Counts of events → SUM/COUNT. Per-slot intensity → AVERAGE. Rates (shares) → DIVIDE of two sums, never AVERAGE of the ratio column. Write the expected check value (189.5, +64.9%) as a comment; verify each measure on a card before it enters a chart.

This single visual is the crown jewel of transit analytics: the Working Day line forms an unmistakable "M" shape spiking at Hour 8 (477.0) and Hour 17 (525.3), while the Weekend / Holiday line forms a smooth hill peaking at Hour 13 (372.7)!

💡 Why do we do this?

Reason: The client's #1 complaint is temporal ("vans arrive too late"), so the report must show demand AS A FUNCTION OF TIME — and as two lines (Working Day vs Weekend/Holiday) on one shared axis, because the comparison between commuter rhythm and leisure rhythm IS the insight. One axis, two curves: differences are read directly, no mental chart-jumping.

Real-time example: Read the "M" shape operationally: demand surges 7–9am and 4–6pm, so rebalancing vans must pre-position bikes before the spikes (say 6:30am and 3:30pm) — reactive afternoon dispatch is provably too late when Hour 17 hits 525 rides. The weekend hill says the opposite schedule: docks drain gradually toward a 1pm peak, so morning van routes can double as maintenance runs. Two very different playbooks from two lines that never needed a single spreadsheet formula.

What happens if you skip it: A single averaged line (all days mixed) produces a bland mid-shape around 189.5 rides/hr — hiding BOTH peaks entirely. The van schedules stay wrong, and the client's original complaint remains unaddressed even after the dashboard ships.

Smart-work tip: Keep hr as a continuous 0–23 axis so the curves flow; split categories via Legend (DayType), not via two separate charts. And when a shape (the "M") IS the message, add a text note or data labels at the peaks — callouts guide the reader to the exact hours the client must act on.

  2. Right-click [Avg Hourly Rides] in Values → Conditional formatting → Background color → Gradient from pale cream (Minimum) → amber (Middle) → deep forest green (Maximum).

💡 Why do we do this?

Reason: A 24-hour × 7-day grid is 168 numbers — far beyond what any human reads as digits, but instantly readable as a color field. A native Matrix + gradient conditional formatting turns those numbers into a heatmap WITHOUT downloading any marketplace visual — proving that format settings, not plugins, solve most "we need a special chart" requests. Turning subtotals off keeps the color scale comparing hours-to-hours instead of mixing in giant row/col totals.

Real-time example: Watch a dispatcher use it: the right side of the grid (Tue–Fri) glows deep green in two horizontal bands — rows 8 and 17 — while the Sunday column stays pale cream almost all day. Those two dark bands are exactly where vans must stand guard; the pale blocks (midnight–6am, Sunday mornings) are the safe maintenance windows the Director asked to schedule during wet shifts. One glance answers "when" and "when NOT to send vans" — no reading required.

What happens if you skip it: Mistake 3 strikes: subtotals left ON turn the Grand Total dark green and wash every real hourly cell pale — the heatmap becomes a mostly-white grid with one blazing corner. Also, a plain matrix of 168 numbers gets scrolled past unread.

Smart-work tip: When applying the gradient, set "Apply to" = Values only (exclude totals) and pin min/mid/max colors — the middle anchor (amber) prevents the "everything looks light-green" wash. Numbers-on-color beats color-only for ops teams: dispatchers need the exact count, not just the vibe.

Visual 4, 5 & 6 Monthly Stacked Column + Weather Combo + Rider Mix Donut

1. Stacked column chart: X-axis = Calendar[YearMonth], Y-axis = [Registered Rides] & [Casual Rides].
2. Line and clustered column chart: X-axis = Trips[WeatherLabel], Column y-axis = [Avg Hourly Rides] (204.9 → 175.2 → 111.6 → 74.3), Line y-axis = [Casual Share %] (watch casual riders vanish during rain while registered commuters keep riding!).
3. Donut chart: Values = [Registered Rides] and [Casual Rides].

💡 Why do we do this?

Reason: Three visuals, three distinct questions. The 24-month stacked columns answer "how fast are we growing, and WHO is driving it?" (volume + mix in one chart). The weather combo answers "what does rain cost us, and to whom?" — the line of Casual Share % on top of the ride-count columns separates volume loss from behavior change. The 2-slice donut anchors the strategic fact: this is a membership business (81.2%), not a tourism business (18.8%).

Real-time example: The weather combo carries a subtle gem the client explicitly asked about: from Clear to Light Rain, columns fall 204.9 → 111.6 rides/hr — but the Casual Share line collapses even faster, because tourists simply stay home while registered commuters still need to reach work (and the -45.5% rain drop from the profile is mostly casuals). Operationally that means maintenance during wet hours costs few members their commute — exactly the wet-shift maintenance window the Director wanted quantified. The stacked columns add the growth angle: the Registered band widens steadily through 2012 while Casual stays nearly flat — growth is coming from converts to membership.

What happens if you skip it: "Rain cuts demand" stays a vague feeling instead of a quantified -45.5% with a rider-mix explanation; budgeting for bike purchases and marketing keeps treating casual surges as the growth engine when the member base is.

Smart-work tip: When a drop could be "fewer people" or "different people", plot the volume AND the share together — columns + line. And keep the donut at exactly 2–3 slices; it's a strategic mix headline, not a data exploration tool.

8. Trainer's Troubleshooting: Common Beginner Mistakes

Mistake 1 — Loading both day.csv and hour.csv and relating them on dteday: One day matches 24 hours, creating a trap where daily numbers multiply 24× or cross-filters break. Always keep one fact table per grain!
Mistake 2 — Summing temp or hum: Adding 24 hourly temperatures together gives "14.2 normalized degrees." Always use AVERAGE() for weather readings!
Mistake 3 — Subtotals washing out the Heatmap Matrix colors: If Row/Column subtotals are left ON and conditional formatting includes totals, the Grand Total turns dark green and all 168 hourly cells turn pale white! Always set Conditional Formatting "Apply to" = Values only (not Totals).
